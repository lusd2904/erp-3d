### 0.3 与《平台开发约定》V0.1 的对齐说明（人工核对）

约定文件：`/workspace/erp-3d/fullsys/code/docs/平台开发约定.md`（V0.1）。正文与本节冲突时，**以本节与约定为准**。

1. **建表**：单据/基础资料表（`andon_ticket`、`andon_prevent_track`、`smt_station_table`、`smt_feed_table`、`eqp_equipment` 等）用 BillMeta（snake_case）+ `ensureBillTables(qr, META)`；非单据系统记录表用 `ensureTable/addColumnIfMissing/addIndexIfMissing`。迁移放 `apps/api/src/db/migrations/` 并登记 `ALL_MIGRATIONS`，必须幂等，禁止 DROP、禁止改列类型。正文 DDL 只作字段对照。
2. **模块**：代码在 `apps/api/src/eqp/`（设备、采集、OEE、安灯、SMT、消息队列）；`onModuleInit` 里 `BillEngineRegistry.registerBill(...)`。钩子只用 `beforeSave/afterSave/beforeAudit/afterAudit/beforeUnaudit/afterUnaudit/beforeCancel/afterCancel/beforeDelete/rowGuards`；WebSocket、MQTT 发布用 `DbService.afterCommit`。TypeORM DataSource + DbService 原生 SQL，不用 Repository。
3. **状态**：头表 `status` 只有 `DRAFT/CREATED/AUDITING/AUDITED/REAUDIT`；关闭/作废改 `close_status/cancel_status`（A/B）。已审核须先反审核才能作废；有下游有效单据禁止反审核（`BIZ_HAS_DOWNSTREAM`）。安灯的业务进度（待处理/处理中/已关闭）放在 `biz_status`，不占用头表 `status`。
4. **反写**：`srcForm` = 被反写的上游，`tgtForm` = 触发反写的下游；两段反写（保存写关联数量，审核写执行数量）；表达式禁止 SQL 子查询。设备计数生成工序汇报单走 WP12 的服务与规则，本 WP 不另定义对工序计划的反写；业务模块不得直接 UPDATE 上游单据数量。
5. **接口**：`/api/v1`；响应 `{code,msg,data,traceId,errors?}`；DECIMAL 为 string；时间 `YYYY-MM-DD HH:mm:ss.SSS`（无 Z）；写操作支持 `Idempotency-Key`；WebSocket 为 Socket.IO `/ws`。MQTT topic `plant/{org}/eqp/{eqpId}/{status|counter|param}`（二期 `unit`、`changeover`）；控制通道 `plant/{org}/sim/{eqpId}/{inject|rate|task}`，其中 `task` 是生产用（来自 `eqp_task_rt`），`inject/rate` 与 `/api/v1/sim/*` 只在测试环境开放。
6. **三维状态**：金蝶 5 态 `PROCESSING/ABNORMAL_STOP/IDLE/OCCUPIED/OFF` → 三维 `run/fault/idle/maint/off`（off 灰色，Q18）；MQTT code `RUN/IDLE/ALARM/OFF`。界面不得出现“演示数据”；断线显示“连接中断”并保留最后状态。

| 执行中 | `ACTIVE` | 生产中 | 实时更新 `output_qty, yield_qty, oee_*` |
| 完工待机 | `WAIT_DONE` | 完工事件/数量达标 | 停止计数，保留最后状态 |
| 移交/结束 | `CLOSED` | 移交下道工序/手工结束 | 从 `eqp_task_rt` 删除，归档至 `eqp_task_his` |

**关键约束（E13）**：
- `eqp_task_rt` 创建/删除时发布 `plant/{org}/sim/{eqpId}/task` 消息，模拟器据此决定是否计数
- `inject`（注入故障/待料）和 `rate`（倍率）两个控制 topic 及 `/api/v1/sim/*` REST **仅测试环境开放**
- 断线时前端显示“连接中断”，保留最后状态，**不回退成固定动画**（C-13）

## ③ 转换与反写规则


> 【核对】K04：CNV-EQP-RPT 的 `srcForm=eqp_point_value` 不是单据，不能注册为 ConvertRuleConfig；实施为采集服务在事务内调用 WP12 的 `autoReportCounterDelta`（见 WP12 4.3），汇报单 `source=EQP` 自动提交+审核，反写复用 WP12 规则。K05：R43 原意是“可上料数量 = 领料 + 补料 − 已上料”（只读引用 WP10/WP06 数量，由上料流水计算，见 5.4.3），不是“上料流水→工位剩余”；上料流水改工位剩余是 WP13 内部服务逻辑，`station_material_stock` 是非单据表，不走 WritebackRule。正文引用的 `qty_on_hand`、`prevent_required`、`current_step`、`alarm_level`、`fault_category`、`business_status` 在 DDL 中不存在（DDL 为 `qty_loaded/qty_consumed`、`level`、`stage_id`、`biz_status`）；`filterExpr` 里 `close_status == 'CLOSED'` 应为 `'B'`。`prevent_required` 是否加列列入待确认。

### 1. 规则清单总览

| 编号 | 规则代码 | 规则类型 | 触发方向 (srcForm → tgtForm) | 业务场景 | 核心约束 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | CNV-EQP-RPT | Convert | `eqp_point_value` (虚拟源) → `sfc_report` | R11 设备计数点自动生成工序汇报单 | 仅生成单据，反写复用 WP12 规则；source=EQP；保存后自动提交审核 |
| 2 | CNV-ANDON-PREVENT | Convert | `andon_ticket` → `andon_prevent_track` | R42 安灯单关闭/处理完毕 → 生成预防措施跟踪单 | 源单据状态=业务CLOSED；目标单据挂 SM-01 审批流 |
| 3 | WB-SMT-FEED-STOCK | Writeback | `smt_station_table_entry` ← `smt_feed_log` | R43/SMT 上料流水 → 扣减工位剩余库存 | 非单据表反写，走钩子 `afterSave`/`afterDelete`，非引擎标准反写 |
| 4 | WB-ANDON-GEN | Hook (非标准转换) | `eqp_event_handler` → `andon_ticket` | 设备自动报警/人工发起 → 生成安灯单 | 非 ConvertRule，由 `eqpEventService` 在事务内直接创建单据 |

> **方向约定提醒**：ConvertRule `srcForm`=来源单据，`tgtForm`=目标单据（下推方向）；WritebackRule `srcForm`=被反写的**上游**单据，`tgtForm`=触发反写的**下游**单据（与下推方向相反）【依据:平台开发约定 6.2】。

### 4. WB-SMT-FEED-STOCK：SMT 上料流水 → 工位剩余库存 (R43)

**业务说明**：`smt_feed_log` 记录每次上料/下料实绩。工位剩余表 `station_material_stock` 为**非单据系统记录表**，不走标准 `WritebackRuleConfig`（引擎仅支持单据间反写）。由 `SmtFeedService` 在 `smt_feed_log` 变更事务内，通过钩子/服务逻辑直接 `UPDATE station_material_stock` 扣减/回滚剩余数量【依据:需求说明书 8.4 R43、平台开发约定 I.1、I.4、人工核对事实 E11】。

#### 4.1 伪反写规则定义 (仅作设计对照，不注册引擎)

```typescript
// 设计对照：实际不注册 WritebackRuleConfig，由服务代码实现
const WB_SMT_FEED_STOCK_DESIGN = {
  code: 'WB-SMT-FEED-STOCK',
  name: 'SMT上料流水扣减工位剩余库存',
  srcForm: 'station_material_stock',   // 被反写的上游（库存视角）
  tgtForm: 'smt_feed_log',             // 触发反写的下游（流水视角）
  srcField: 'qty_on_hand',             // 上游被更新列：在手数量
  tgtValue: 'CASE WHEN feed_type IN (\'LOAD\',\'REPLENISH\') THEN -feed_qty ELSE feed_qty END', // 下游取值：上料扣减，下料/退料增加
  onEvent: 'save',                     // 保存流水即时更新剩余
  mode: 'add',                         // 增量模式：qty_on_hand += tgtValue
  overCtrl: 'FORBID',                  // 禁止剩余<0（由 rowGuards 校验）
  overExpr: 'qty_on_hand + tgtValue >= 0',
  closeExpr: undefined,
  closeScope: 'NONE',
  // 反审核/作废/删除释放：smt_feed_log 无审核流，仅有作废/删除
  // beforeDelete/afterCancel 钩子中执行反向加回
};
```

#### 4.2 字段映射与计算逻辑
| 操作类型 `feed_type` | `smt_feed_log.feed_qty` 符号 | `station_material_stock.qty_on_hand` 变化 | `qty_consumed` 变化 |
| :--- | :--- | :--- | :--- |
| `LOAD` (首次上料) | +N | -N | +N |
| `REPLENISH` (补料) | +N | -N | +N |
| `UNLOAD` (下料/退料) | +N | +N | -N (按实际良品退回扣减消耗) |
| `SCRAP` (报废清料) | +N | +N | 0 (消耗不变，仅剩余回升) |

> **可上料数量校验 (R43)**：PDA 上料时实时计算 `可上料 = 领料数量 + 补料数量 - 已上料数量`。
> - 领料数量：`pp_pick_entry` (WP06) `base_qty` 汇总（只读引用）
> - 补料数量：`pp_feed_entry` (WP10) `base_qty` 汇总（只读引用）
> - 已上料数量：`smt_feed_log` WHERE `feed_type IN ('LOAD','REPLENISH')` SUM(`feed_qty`)【依据:人工核对事实 E11】。

#### 4.3 钩子实现要点 (Service 层事务内)
注册于 `smt_feed_log` 服务 (`SmtFeedService`)，非标准 BillHooks。

| 操作 | 处理逻辑 | 【依据】 |
| :--- | :--- | :--- |
| `createFeedLog` (上料/补料) | 1. 校验 `qty_on_hand >= feed_qty` (FORBID 负库存)；2. `UPDATE station_material_stock SET qty_on_hand = qty_on_hand - feed_qty, qty_consumed = qty_consumed + feed_qty, last_feed_time=now() WHERE id=...`；3. 写入 `smt_feed_log`。 | 【依据:需求说明书 8.4 R43】 |
| `createUnloadLog` (下料) | 1. `UPDATE station_material_stock SET qty_on_hand = qty_on_hand + feed_qty, qty_consumed = qty_consumed - feed_qty WHERE id=...`；2. 写入 `smt_feed_log`。 | 【依据:需求说明书 8.4 R43】 |
| `cancelFeedLog` / `deleteFeedLog` | 反向执行上述 UPDATE，回滚 `qty_on_hand` 与 `qty_consumed`。 | 【依据:平台开发约定 6.5 删除释放占用】 |

### 5. WB-ANDON-GEN：设备自动报警/人工发起 → 安灯单生成 (钩子)

**业务说明**：非标准转换规则。设备采集到故障/报警事件 (`eqp_event_def.trigger_type='ALARM'`) 或 PC/终端人工发起安灯时，由 `EqpEventService` / `AndonService` 在事务内直接创建 `andon_ticket` 单据，并初始化处理路径步骤 (`andon_step_log`)、截止时间 (`andon_deadline`)。不走 `ConvertRuleConfig`【依据:需求说明书 8.3 安灯管理、金蝶 现场异常处理单、平台开发约定 I.1】。

#### 5.1 触发时机与入口
| 触发源 | 入口服务 | 关键参数 |
| :--- | :--- | :--- |
| 设备 MQTT 报警上报 | `EqpMqttService.onAlarm()` → `EqpEventService.handleAlarm()` | `equipment_id`, `event_code` (映射 `eqp_event_def.code`), `alarm_level`, `alarm_msg` |
| PC 端手工发起 | `AndonController.createManual()` | `equipment_id`, `line_id`, `fault_category`, `fault_code`, `description`, `initiator_id` |
| 终端扫码/按钮 | `AndonController.createFromTerminal()` | 同手工发起 |

#### 5.2 单据创建逻辑 (事务内)
```typescript
// EqpEventService / AndonService 伪代码逻辑
async function createAndonTicket(params: AndonCreateParams, ctx: DbContext) {
  // 1. 解析事件定义与处理路径
  const evtDef = await ctx.db.selectOne('eqp_event_def', { code: params.event_code, org_id: params.org_id });
  const path = await ctx.db.select('eqp_event_path', { event_def_id: evtDef.id, enabled: 1 }, 'step_no ASC');
  
  // 2. 生成安灯单头
  const ticketId = snowflake.nextId();
  await ctx.db.insert('andon_ticket', {
    id: ticketId, org_id: params.org_id,
    bill_no: genBillNo('AND', params.org_id), // AND26111300001
    bill_date: now(), biz_date: today(),
    bill_type_id: 'ANDON_TICKET',
    status: 'DRAFT', // 头状态走标准流，业务状态由 SM-10 管理
    close_status: 'A', cancel_status: 'A',
    equipment_id: params.equipment_id,
    line_id: params.line_id,
    fault_category: params.fault_category,
    fault_code: params.fault_code,
    fault_desc: params.alarm_msg || params.description,
    alarm_level: params.alarm_level || evtDef.alarm_level,
    source: params.source || 'EQP', // EQP/MANUAL
    initiator_id: params.initiator_id,
    handler_id: path[0]?.handler_id, // 首节点处理人
    current_step: 1,
    business_status: 'PENDING', // SM-10 初始状态
    prevent_required: false, // 初始不需预防，处理完毕时由处理人勾选
    remark: params.remark,
    version: 0, creator_id: params.user_id, created_at: now()
  });

  // 3. 初始化步骤日志
  for (const step of path) {
    await ctx.db.insert('andon_step_log', {
      id: snowflake.nextId(), ticket_id: ticketId,
      step_no: step.step_no, step_name: step.step_name,
      handler_id: step.handler_id, handler_role: step.handler_role,
      sla_minutes: step.sla_minutes,
      status: step.step_no === 1 ? 'HANDLING' : 'PENDING',
      started_at: step.step_no === 1 ? now() : null
    });
  }

  // 4. 计算首节点截止时间，写入 andon_deadline
  const firstStep = path[0];
  if (firstStep?.sla_minutes) {
    await ctx.db.insert('andon_deadline', {
      id: snowflake.nextId(), ticket_id: ticketId,
      step_no: 1, deadline_at: addMinutes(now(), firstStep.sla_minutes),
      escalated: 0
    });
  }

  // 5. 保存后自动提交审核 (需求 P03/E5: 安灯单保存后自动提交、提交后自动审核)
  // 调用 BillEngine.submit/audit 或直接走钩子 afterSave 发布事件
  await billEngine.submit('andon_ticket', ticketId, { userId: params.user_id });
  await billEngine.audit('andon_ticket', ticketId, { userId: params.user_id });

  // 6. 发布 WebSocket 实时推送 (afterCommit)
  DbService.afterCommit(() => wsServer.to(`andon:${params.org_id}`).emit('andon.created', { ticketId }));
  
  return ticketId;
}
```

#### 4.1.6 Mosquitto 配置要点
- **部署**：与 ERP 程序同装在 `ib-v6`，仅开放 Docker 内网端口（1883/8883），不暴露宿主机/公网【依据:待老板确认 Q08】【依据:技术方案 1.2 表格以 Q08 为准】
- **账号与 ACL**：
  - `sim-plant`（模拟器服务）：
    - `publish`：`plant/+/eqp/#`（上报 status/counter/param/unit/changeover）
    - `subscribe`：`plant/+/sim/#`（接收 inject/rate/task）
  - `erp-ingest`（ERP 采集服务）：
    - `subscribe`：`plant/+/eqp/#`（只读设备上报）
    - `publish`：`plant/+/sim/#`（下发控制指令，仅测试环境）
- **持久化**：`/mosquitto/data`、`/mosquitto/log` 挂载宿主机目录
- **配置片段**（`mosquitto.conf` 关键段）：
```
listener 1883
allow_anonymous false
persistence true
persistence_location /mosquitto/data/
log_dest file /mosquitto/log/mosquitto.log
log_type all

# ACL 文件
acl_file /mosquitto/config/acl.conf
password_file /mosquitto/config/passwd.conf
```
- **acl.conf 示例**：
```
# sim-plant
user sim-plant
topic write plant/+/eqp/#
topic read plant/+/sim/#

# erp-ingest
user erp-ingest
topic read plant/+/eqp/#
topic write plant/+/sim/#
```

---


> 【核对】K07：任务书要求 `erp-ingest` 只读；但 `task` 控制通道需后端发布。建议拆账号：`erp-ingest` 只读 `plant/+/eqp/#`；`erp-ctl` 只写 `plant/+/sim/+/task`；`inject/rate` 的写权限只在测试环境 ACL 中开放给测试账号。

### 4.2 WebSocket

#### 4.2.1 连接规范
- **协议**：Socket.IO v4
- **路径**：`/ws`（经 nginx 反代，技术方案架构图 `/ws` 路径）【依据:技术方案 2】【依据:共享约定 E10】
- **握手**：`{ auth: { token: "<JWT>" } }`，服务端校验 JWT、解析 `userId`、`orgId`、`roles`
- **房间命名**（自动加入）：
  - `line:{lineId}` —— 产线级订阅（状态、OEE、安灯、物料）
  - `eqp:{eqpId}` —— 设备级订阅（参数、单元状态）
  - `andon:{orgId}` —— 安灯全域订阅
  - `kpi:{lineId}` —— KPI 看板订阅
  - `user:{userId}` —— 个人消息
- **时间格式**：所有推送/响应中的时间字段统一 `YYYY-MM-DD HH:mm:ss.SSS`，**禁止带 Z 的 UTC ISO**【依据:平台开发约定 4.4】【依据:共享约定 E10】
- **DECIMAL**：接口层一律 `string`【依据:平台开发约定 4.4】
- **心跳**：客户端 25s 一次 `ping`，服务端 60s 无响应断开

#### 4.2.2 事件清单

| 事件名 | 触发时机 | 房间 | 节流 | 说明 |
|--------|----------|------|------|------|
| `eqp.status` | 设备状态变更（MQTT status 处理后） | `line:{lineId}`、`eqp:{eqpId}`、`kpi:{lineId}` | 500ms/设备 | 三维状态 run/idle/fault/maint/off + kdStatus |
| `eqp.oee` | OEE 实时计算完成（counter 处理后、定时聚合） | `line:{lineId}`、`kpi:{lineId}` | 2s/产线 | availability/performance/quality/oee、负荷时间、损失时间 |
| `eqp.param` | 参数上报且入库后 | `eqp:{eqpId}`、`line:{lineId}` | 1s/设备 | 实测值、阈值状态（NORMAL/WARN/ALARM） |
| `andon.ticket` | 安灯单创建/派工/处理/关闭/升级 | `andon:{orgId}`、`line:{lineId}`、`user:{handlerId}` | 无（即时） | 单据生命周期 + 步骤日志 |
| `station.material` | 工位物料库存变动（上料/消耗/补料/盘点） | `line:{lineId}`、`user:{operatorId}` | 1s/工位 | 可上料数量、当前库存、预警阈值 |
| `eqp.task` | 实时任务创建/开始/暂停/结束/移交 | `line:{lineId}`、`eqp:{eqpId}`、`kpi:{lineId}` | 无 | `eqp_task_rt` 状态变更 |
| `system.alert` | 系统级告警（MQTT 断线、模拟器异常、OEE 阈值跌破） | `andon:{orgId}`、`user:{adminId}` | 无 | 运维告警 |

#### 4.2.4 服务端实现要点
- **模块位置**：`apps/api/src/eqp/gateways/eqp.gateway.ts`（NestJS + Socket.IO）
- **鉴权**：`WsJwtGuard` 解析 `client.handshake.auth.token`，挂载 `client.user`（含 `userId`、`orgId`、`roles`、`lineIds[]`）
- **房间自动加入**：连接成功后按 `user.orgId`、`user.lineIds` 加入 `andon:{orgId}`、`line:{lineId}`、`kpi:{lineId}`、`user:{userId}`
- **发布入口**：`EqpWsService` 提供 `emitStatus`、`emitOee`、`emitParam`、`emitAndon`、`emitMaterial`、`emitTask`、`emitAlert`，内部调用 `server.to(room).emit(event, payload)`
- **节流**：用 `rxjs` `throttleTime`/`auditTime` 按 `eqpId`/`lineId`/`stationId` 分桶
- **幂等**：推送 payload 含 `ts` 与 `alertId`/`ticketId`/`taskId`，前端去重
- **断线保留**：MQTT 断线 30s 后触发 `system.alert`（CRITICAL），前端显示“连接中断”保留最后状态，**不回退成固定动画**【依据:人工核对事实 4】【依据:需求 1.2 C-13】

### 4.3 REST

> **统一约定**  
> - 前缀：`/api/v1`  
> - 响应体：`{ code, msg, data, traceId, errors? }`，成功时 `code='OK'` 且 `msg=''`  
> - DECIMAL 以 **string** 传输；DATE=`YYYY-MM-DD`；DATETIME(3)=`YYYY-MM-DD HH:mm:ss.SSS`  
> - 写操作支持 `Idempotency-Key` 头；PUT/保存带 `version` 乐观锁，冲突返回 `BIZ_VERSION_CONFLICT`  
> - 权限项格式：`eqp:<resource>:<action>`（如 `eqp:equipment:read`）  
> - 通用单据接口（CRUD、审核、反审核、关闭、作废、执行至、元数据）已在 4.1 定义，**仅列 form + 专有 op**，不再展开字段级 Schema

## ⑤ 算法

### 5.1 采集处理管道

#### 5.1.1 总体流程
```
MQTT 消息 (topic: plant/{org}/eqp/{eqpId}/data)
   │
   ▼
MQTT 订阅服务 (apps/api/src/eqp/services/mqtt-ingest.service.ts)
   │
   ├─ 解码 payload (JSON) → 原始点位数组 [{point_code, value, ts, quality}]
   │
   ├─ 持久化 eqp_point_value (批量 upsert，主键 eqp_id+point_code+ts)
   │
   ├─ 按 point_code 查 eqp_point.process_type 路由
   │     ├─ STATUS  → 状态处理器
   │     ├─ COUNTER → 计数处理器 (5.2)
   │     ├─ PARAM   → 参数归档 (仅写 eqp_point_value，不触发事件)
   │     └─ ALARM   → 告警处理器 (生成 andon_ticket，见 WP13-④)
   │
   └─ 统一异常捕获 → 写 mq_message (status=FAILED) + 记录 traceId
```

#### 5.1.2 状态代码映射与生产事件生成

**映射表**：`eqp_status_map`（设备侧代码 → 内部 kdStatus）
| 列 | 说明 |
|---|---|
| eqp_id | 设备 ID |
| src_code | 设备上报代码 (RUN/IDLE/ALARM/OFF 等) |
| kd_status | 目标 kdStatus (PROCESSING/ABNORMAL_STOP/IDLE/OCCUPIED/OFF) |
| event_def_id | 触发的生产事件定义 ID (FK eqp_event_def) |
| priority | 同 src_code 多条映射时的优先级，数值越小越优先 |

**处理伪代码**：
```typescript
async function handleStatusPoint(eqpId: string, point: PointValue, ctx: DbContext) {
  // 1. 查映射
  const maps = await ctx.query(`
    SELECT m.*, d.oee_time_type, d.name AS event_name
    FROM eqp_status_map m
    JOIN eqp_event_def d ON d.id = m.event_def_id
    WHERE m.eqp_id = ? AND m.src_code = ?
    ORDER BY m.priority ASC
  `, [eqpId, point.value]);

  if (maps.length === 0) {
    // 找不到映射：写入 eqp_point_value 已完成，记录告警日志，不生成事件
    await logUnmappedStatus(eqpId, point.value, point.ts, ctx);
    return;
  }

  // 2. 取最高优先级映射
  const map = maps[0];
  const newKdStatus = map.kd_status;
  const eventDefId = map.event_def_id;
  const oeeTimeType = map.oee_time_type; // VALID/PLAN_STOP/REST/DOWN_LOSS

  // 3. 读取当前设备状态 (eqp_equipment.kd_status, status_start_at)
  const equip = await ctx.queryOne(`SELECT kd_status, status_start_at FROM eqp_equipment WHERE id=?`, [eqpId]);
  const oldKdStatus = equip.kd_status;
  const statusStartAt = equip.status_start_at; // DATETIME(3)

  // 4. 去重：同 kdStatus 且 ts <= status_start_at 视为重复/乱序旧数据，丢弃
  if (newKdStatus === oldKdStatus && point.ts <= statusStartAt) {
    return; // 静默丢弃，已在 eqp_point_value 留痕
  }

  // 5. 乱序保护：ts < status_start_at 但状态不同 → 视为网络抖动，按 ts 处理但不回退状态起点
  const effectiveTs = point.ts < statusStartAt ? statusStartAt : point.ts;

  // 6. 状态变更：写 eqp_status_log (旧段结束、新段开始)
  await ctx.exec(`
    INSERT INTO eqp_status_log (id, org_id, eqp_id, kd_status, oee_time_type, start_at, end_at, event_def_id, src_point_ts, remark)
    VALUES (?,?,?,?,?,?,?,?,?,?)
  `, [snowflake(), orgId, eqpId, oldKdStatus, getOeeTimeType(oldKdStatus), statusStartAt, effectiveTs, lastEventDefId, point.ts, '状态切换']);

  await ctx.exec(`
    INSERT INTO eqp_status_log (id, org_id, eqp_id, kd_status, oee_time_type, start_at, event_def_id, src_point_ts, remark)
    VALUES (?,?,?,?,?,?,?,?,?)
  `, [snowflake(), orgId, eqpId, newKdStatus, oeeTimeType, effectiveTs, eventDefId, point.ts, '状态切换']);

  // 7. 更新设备当前状态
  await ctx.exec(`UPDATE eqp_equipment SET kd_status=?, status_start_at=?, last_event_def_id=? WHERE id=?`,
    [newKdStatus, effectiveTs, eventDefId, eqpId]);

  // 8. 发布 WebSocket eqp.status (room: eqp:{eqpId})
  await wsServer.emit('eqp.status', { eqpId, kdStatus: newKdStatus, ts: effectiveTs, threeDim: kdToThreeDim(newKdStatus) });

  // 9. 若新状态为 ABNORMAL_STOP 且有故障码点位并行到达 → 交由故障映射处理 (5.1.3)
}
```

**边界条件**：
- 设备首次上线：`eqp_equipment.kd_status` 为 NULL，`status_start_at` 为 NULL → 直接写入新段，`start_at = point.ts`。
- 映射缺失：不阻断管道，记录 `mq_message` (code=UNMAPPED_STATUS) 供运维排查。
- 乱序窗口：仅保护 `status_start_at` 之前的旧数据；允许同一状态内的乱序（如心跳重复上报）。
- 事务边界：单条 MQTT 消息内的所有点位在同一 DB 事务处理；跨消息不保证顺序，靠 `ts` 与 `status_start_at` 校正。

#### 5.1.3 故障代码映射

**映射表**：`eqp_fault_map`
| 列 | 说明 |
|---|---|
| eqp_id | 设备 ID |
| fault_code | 设备上报故障代码 (字符串) |
| event_def_id | 关联生产事件定义 (通常为设备故障/程序故障) |
| auto_create_andon | BOOL，是否自动创建安灯单 |
| andon_type_id | 安灯类型 ID (FK andon_type) |

**处理逻辑**：
- 仅在 `kd_status = ABNORMAL_STOP` 且收到 `FAULT_CODE` 类型点位时触发。
- 查 `eqp_fault_map`，找不到 → 记录 `mq_message` (UNMAPPED_FAULT)，仍生成通用“设备故障”事件（取设备默认故障事件定义）。
- 找到 → 生成对应事件，若 `auto_create_andon=true` 则调用安灯创建服务（WP13-④）。

#### 5.1.4 断线/心跳超时处理

**配置**：`eqp_equipment.heartbeat_timeout_sec` (默认 60s)，`eqp_equipment.offline_grace_sec` (默认 300s)。

**定时任务** (每 10 秒扫描)：
```sql
SELECT id, org_id, kd_status, status_start_at, last_heartbeat_at
FROM eqp_equipment
WHERE last_heartbeat_at < DATE_SUB(NOW(3), INTERVAL heartbeat_timeout_sec SECOND)
  AND kd_status <> 'OFF';
```

**处理**：
1. 若 `NOW - last_heartbeat_at <= offline_grace_sec`：写入 `eqp_status_log` 一段 `kd_status=IDLE, oee_time_type=DOWN_LOSS, event_def_id=HEARTBEAT_LOSS`，设备 `kd_status` 改为 `IDLE`，前端显示“连接中断”并保留最后已知参数/产量（不回退动画）。
2. 若 `> offline_grace_sec`：写入 `kd_status=OFF, oee_time_type=REST`，设备 `kd_status=OFF`，前端显示“离线”。
3. 恢复：收到新 MQTT 消息时，按 5.1.2 正常切换状态，`start_at` 取消息 `ts`。

### 5.2 计数自动报工

#### 5.2.1 核心概念
| 概念 | 说明 |
|---|---|
| **开工基准** | 任务在 `eqp_task_rt` 创建时（开工/接班），读取设备当前 `total_output` 计数器值记为 `counter_start`。 |
| **差值** | `delta = current_counter - counter_start`（处理溢出复位）。 |
| **溢出复位** | 设备计数器为 32 位无符号整数，最大值 4,294,967,295。若 `current < counter_start` 则 `delta = (MAX_UINT32 - counter_start + 1) + current`。 |
| **NG 计入** | 总产量 = OK + NG。设备若上报 `good_count`/`reject_count` 两路，`total = good + reject`；若仅上报 `total`+`good`，则 `reject = total - good`。 |
| **不停机交接班** | 先采集再移交：旧任务 `end_at = now`，写 `eqp_task_his`；新任务 `counter_start = current_counter`，创建 `eqp_task_rt`。中间无计数丢失。 |
| **完工待机/结束任务** | 任务完成数量达标或人工结束 → 写 `eqp_task_his`，删除 `eqp_task_rt`，设备进入 `IDLE`/`OCCUPIED`。 |

#### 5.2.2 计数处理器伪代码
```typescript
async function handleCounterPoint(eqpId: string, point: PointValue, ctx: DbContext) {
  // 1. 取当前运行任务
  const task = await ctx.queryOne(`
    SELECT id, op_plan_entry_id, dispatch_entry_id, counter_start, last_counter, ok_qty, ng_qty, total_qty
    FROM eqp_task_rt WHERE eqp_id = ? AND status = 'RUNNING'
  `, [eqpId]);
  if (!task) return; // 无任务不计数

  // 2. 解析点位值
  const { total, good, reject } = parseCounterPayload(point.value); // 兼容单/双路
  const currentTotal = total ?? (good + reject);
  const currentGood = good ?? (currentTotal - (reject ?? 0));

  // 3. 溢出复位 delta
  let deltaTotal: number, deltaGood: number;
  if (currentTotal >= task.last_counter) {
    deltaTotal = currentTotal - task.last_counter;
  } else {
    // 溢出
    deltaTotal = (UINT32_MAX - task.last_counter + 1) + currentTotal;
  }
  // good 同理（若设备不单独上报 good，按良率比例分摊或全算 OK，配置化）
  if (good !== undefined) {
    deltaGood = currentGood >= task.last_good ? currentGood - task.last_good : (UINT32_MAX - task.last_good + 1) + currentGood;
  } else {
    deltaGood = Math.round(deltaTotal * (task.ok_qty / task.total_qty || 1)); // 兜底
  }
  const deltaNg = deltaTotal - deltaGood;

  // 4. 累加到任务
  const newTotal = task.total_qty + deltaTotal;
  const newOk = task.ok_qty + deltaGood;
  const newNg = task.ng_qty + deltaNg;

  await ctx.exec(`
    UPDATE eqp_task_rt SET last_counter=?, last_good=?, total_qty=?, ok_qty=?, ng_qty=?, updated_at=NOW(3)
    WHERE id=?
  `, [currentTotal, currentGood, newTotal, newOk, newNg, task.id]);

  // 5. 触发自动报工 (达到报工批量或定时)
  if (shouldAutoReport(task, newTotal)) {
    await autoReportTask(task.id, deltaTotal, deltaGood, deltaNg, ctx);
  }
}
```

### 5.3 OEE 计算

#### 5.3.1 口径定义 (需求 8.5、Q17)

| 时间类型 | 代码 | 说明 | 计入负荷时间 |
|---|---|---|---|
| 有效生产 | VALID | 正常加工、占用(换模/调整) | 是 |
| 计划停机 | PLAN_STOP | 保养、点检、计划性停机 | 否 |
| 休息/非工作 | REST | 午休、交接班、非排班时间、关机 | 否 |
| 损耗停机 | DOWN_LOSS | 故障、待料、生产准备、完工待机、安灯异常 | **是** |

> **待确认**：待料、完工待机归 DOWN_LOSS 还是单独类别（如 WAIT_MATERIAL/FINISH_WAIT）。建议默认归 DOWN_LOSS，若需单独统计可在 `eqp_event_def` 增加细分 `oee_time_type`。

#### 5.3.2 日历与负荷时间

**日历优先级**：
1. 临时日历 `eqp_calendar` (is_temp=1, eqp_id 指定, date 范围)
2. 设备绑定日历 `eqp_equipment.calendar_id` → `eqp_calendar` (is_temp=0)
3. 产线日历 `prod_line.calendar_id`
4. 组织默认日历 `sys_org.default_calendar_id`

**班次段**：日历关联 `eqp_shift` (shift_id, start_time, end_time, is_working)。跨日班次按自然日切分。

**负荷时间计算** (单台设备、单日)：
```
负荷时间 = Σ (班次段 ∩ 工作日历) 的时长 (分钟)
```
非工作日/非排班时间 → REST，不计入负荷时间。

#### 5.3.3 状态日志切段与 OEE 时间类型累计

**数据源**：`eqp_status_log` (kd_status, oee_time_type, start_at, end_at)。

**跨班/跨日切段算法**：
```typescript
function splitSegmentsByCalendar(logs: StatusLog[], calendar: CalendarDay): Segment[] {
  const segments: Segment[] = [];
  for (const log of logs) {
    let cursor = log.start_at;
    while (cursor < (log.end_at || now())) {
      // 找到 cursor 所在的班次段
      const shiftSeg = calendar.findShiftSegment(cursor);
      if (!shiftSeg) { // 非排班时间
        const nextShiftStart = calendar.nextShiftStart(cursor);
        const segEnd = log.end_at && log.end_at < nextShiftStart ? log.end_at : nextShiftStart;
        segments.push({ start: cursor, end: segEnd, oeeTimeType: 'REST', isWorking: false });
        cursor = segEnd;
        continue;
      }
      const segEnd = log.end_at && log.end_at < shiftSeg.end ? log.end_at : shiftSeg.end;
      segments.push({
        start: cursor,
        end: segEnd,
        oeeTimeType: log.oee_time_type,
        isWorking: shiftSeg.is_working,
        kdStatus: log.kd_status,
        eventDefId: log.event_def_id
      });
      cursor = segEnd;
    }
  }
  return segments;
}
```

**累计 (分钟, 保留 1 位小数)**：
```typescript
const acc = { VALID: 0, PLAN_STOP: 0, REST: 0, DOWN_LOSS: 0 };
for (const seg of segments) {
  const minutes = (seg.end - seg.start) / 60000; // ms → min
  if (seg.isWorking) {
    acc[seg.oeeTimeType] += minutes;
  } else {
    acc.REST += minutes; // 非工作时间全记 REST
  }
}
const loadTime = acc.VALID + acc.DOWN_LOSS; // 负荷时间 = 有效 + 损耗
```

#### 5.3.4 理论节拍取值顺序 (Q28)

| 优先级 | 来源 | 字段 |
|---|---|---|
| 1 | 工序计划行 `sfc_op_plan_entry` | `theoretical_takt_sec` |
| 2 | 工艺路线工序 `pl_route_operation` | `takt_sec` |
| 3 | 设备默认 `eqp_equipment.default_takt_sec` | `default_takt_sec` |
| 4 | 系统兜底 | 60 秒/件 |

**取值逻辑**：任务运行期间若切换工序计划行，按当前行取值；无行则按设备默认。

#### 5.3.5 性能率 P 与 质量率 Q

**理论产量** = `loadTime_minutes * 60 / theoretical_takt_sec` (件)。

**实际总产量** = `eqp_task_his.total_qty` (日汇总) + `eqp_task_rt.total_qty` (进行中任务)。

**P** = `实际总产量 / 理论产量`。若 `P > 1` → 标记异常，写 `oee_rt.abnormal_reason='P_GT_1'`，P 取 1 计入 KPI，原值保留 `raw_p`。

**合格数** = `eqp_task_his.ok_qty` + `eqp_task_rt.ok_qty` + **检验单合格数** (WP11 `qm_inspect_decision` 关联同工序计划行/批次的 PASS 数量)。

**总投入数** = 实际总产量 (含 NG)。

**Q** = `合格数 / 总投入数`。若无检验数据，Q=1 (默认全合格)。

**可用率 A** = `VALID / loadTime`。

**OEE** = `A * P * Q`。

#### 5.3.8 数值算例

**场景**：设备 EQP-001，2026-11-13，单班 08:00-20:00 (12h=720min)，午休 12:00-13:00 (60min)，晚班 20:00-08:00 不排产。

| 时段 | 状态 | kdStatus | oeeTimeType | 时长(min) |
|---|---|---|---|---|
| 08:00-10:00 | 正常生产 | PROCESSING | VALID | 120 |
| 10:00-10:30 | 待料 | IDLE | DOWN_LOSS | 30 |
| 10:30-12:00 | 正常生产 | PROCESSING | VALID | 90 |
| 12:00-13:00 | 午休 | IDLE | REST | 60 |
| 13:00-14:00 | 换模 | OCCUPIED | VALID | 60 |
| 14:00-15:30 | 故障 | ABNORMAL_STOP | DOWN_LOSS | 90 |
| 15:30-17:00 | 正常生产 | PROCESSING | VALID | 90 |
| 17:00-18:00 | 完工待机 | IDLE | DOWN_LOSS | 60 |
| 18:00-20:00 | 非排班 | OFF | REST | 120 |

**累计**：
- VALID = 120+90+60+90 = **360 min**
- DOWN_LOSS = 30+90+60 = **180 min**
- PLAN_STOP = 0
- REST = 60+120 = **180 min**
- **负荷时间** = 360 + 180 = **540 min** (9 小时)

**理论节拍**：工序计划行 `theoretical_takt_sec = 30` 秒/件 → 理论产能 = 540 * 60 / 30 = **1080 件**。

**实际产量**：当日 `eqp_task_his.total_qty` = 950 件，`ok_qty` = 930 件，`ng_qty` = 20 件。
**检验补录**：同批次检验单 PASS 940 件 (含人工复判合格 10 件) → **合格数 = 940**。

**计算**：
- A = 360 / 540 = **0.6667** (66.67%)
- P = 950 / 1080 = **0.8796** (87.96%)
- Q = 940 / 950 = **0.9895** (98.95%)
- **OEE = 0.6667 * 0.8796 * 0.9895 = 0.5798 (57.98%)**

## 5.4 SMT 上料防错

### 5.4.1 业务流程与核对粒度
PDA 扫描设备/轨道/飞达/料盘（卷盘码）后，解析卷盘码获取物料信息（WP10 条码主档），按上料表（`smt_station_table_entry`）核对：
- **按物料品种**：仅校验 `material_id` 是否在上料表对应工位/飞达的允许物料清单中。
- **按品种及数量**：在品种校验通过基础上，校验本次上料数量是否超过“可上料数量”（领料+补料−已上料）。
- **飞达规格校验**：当 `smt_station_table_entry.check_feeder_spec = true` 时，必须校验扫描飞达的 `feeder_spec_id` 与上料表行维护的 `feeder_spec_id` 一致。

【依据:需求说明书 8.4、技术方案 3.2.6 #153、G1b 2.3、金蝶 SMT上料防错】

### 5.4.2 卷盘码解析与物料核对公式
```text
输入：barcode（卷盘码）
解析：调用 WP10 条码主档服务 parseBarcode(barcode) → { material_id, lot_no, qty, supplier_id, mfg_date, expiry_date, feeder_spec_id? }
核对：
  1) material_id ∈ 上料表行允许物料集合
  2) 若 check_feeder_spec：feeder_spec_id = 上料表行.feeder_spec_id
  3) 若按数量核对：qty ≤ 可上料数量
```

### 5.4.3 可上料数量实时计算（E11）
```text
可上料数量 = 领料数量 + 补料数量 − 已上料数量
领料数量   = Σ pp_pick_entry.base_qty WHERE src_form='smt_feed_table' AND src_entry_id = 上料表行ID
补料数量   = Σ pp_feed_entry.base_qty  WHERE src_form='smt_feed_table' AND src_entry_id = 上料表行ID
已上料数量 = Σ smt_feed_log.base_qty   WHERE station_table_entry_id = 上料表行ID AND action IN ('LOAD','RELOAD')
```
> 说明：不依赖 WP10 反写 WP13 表，PDA 校验时实时只读查询上述三张表聚合。

【依据:修订单 E11】

### 5.4.4 MSL 状态与先进先出校验（调用 WP10）
```text
调用 WP10 接口：GET /api/v1/wp10/msl/check?material_id=&lot_no=&station_id=
返回：{ allowed: bool, reason_code?, remaining_floor_life_hours? }
拒绝：allowed=false → 返回 reason_code（见 5.4.8 拒绝原因码表）
```

### 5.4.5 上料动作与流水写入
| 动作类型 `action` | 触发条件 | 写入 `smt_feed_log` 关键字段 | 更新 `station_material_stock` |
|---|---|---|---|
| LOAD（首次上料） | 该工位/飞达当前无料 | `station_table_entry_id, feeder_id, material_id, lot_no, base_qty, action='LOAD', operator_id, occur_time` | 若无记录则 INSERT（qty_loaded=base_qty, qty_consumed=0, qty_remaining=base_qty）；有记录则 qty_loaded+=base_qty, qty_remaining+=base_qty |
| RELOAD（续料/换料） | 该工位/飞达有料，扫描同物料/同批次（续料）或不同批次（换料） | 同上，`action='RELOAD'` | qty_loaded+=base_qty, qty_remaining+=base_qty；若换料需记录旧批次剩余量转入 `qty_remaining`（不清零） |
| UNLOAD（下料） | PDA 扫描下料确认 | `action='UNLOAD', base_qty=下料数量` | qty_remaining-=base_qty（不得<0），若 qty_remaining=0 可标记工位空闲 |

> 约束：`smt_feed_log` 仅追加，不修改历史行。`station_material_stock` 由业务服务直接 UPDATE（非单据引擎），同一事务内先写流水再更新库存表。

【依据:技术方案 3.2.6 #153、已建表清单】

### 5.4.6 续料、换料、下料规则
- **续料**：同一 `station_table_entry_id` + 同 `material_id` + 同 `lot_no`，允许叠加；不触发 MSL 重新校验（已在首次上料校验）。
- **换料**：同 `station_table_entry_id`，`material_id` 相同但 `lot_no` 不同，或 `material_id` 不同（需上料表允许替代料）。必须重新走 MSL 校验与可上料数量校验。
- **下料**：仅允许 `qty_remaining > 0` 时执行；下料数量 ≤ `qty_remaining`；下料后若 `qty_remaining=0`，工位状态置为空闲（`smt_feeder.current_material_id=NULL`）。

### 5.4.7 伪代码（PDA 上料校验主流程）
```typescript
async function pdaLoadMaterial(input: { eqpId, stationId, feederId, barcode, action, qty? }) {
  // 1. 解析卷盘码
  const parsed = await wp10.parseBarcode(input.barcode);
  // 2. 取上料表行
  const entry = await db.selectOne('smt_station_table_entry', {
    where: { station_table_id: input.stationId, feeder_id: input.feederId, is_active: 1 }
  });
  if (!entry) throw { code: 'BIZ_SMT_ENTRY_NOT_FOUND' };

  // 3. 物料品种核对
  if (!entry.allowed_material_ids.includes(parsed.material_id))
    throw { code: 'BIZ_SMT_MATERIAL_MISMATCH' };

  // 4. 飞达规格核对
  if (entry.check_feeder_spec && parsed.feeder_spec_id !== entry.feeder_spec_id)
    throw { code: 'BIZ_SMT_FEEDER_SPEC_MISMATCH' };

  // 5. MSL 校验
  const msl = await wp10.checkMsl({ material_id: parsed.material_id, lot_no: parsed.lot_no, station_id: input.stationId });
  if (!msl.allowed) throw { code: msl.reason_code };

  // 6. 数量核对（按品种及数量粒度）
  if (entry.check_qty) {
    const avail = await calcAvailableQty(entry.id);
    if (parsed.qty > avail) throw { code: 'BIZ_SMT_QTY_EXCEED', data: { avail } };
  }

  // 7. 写流水 & 更新工位库存
  await db.tx(async (tx) => {
    await tx.insert('smt_feed_log', { ...common, action: input.action, base_qty: parsed.qty });
    await updateStationStock(tx, entry.id, parsed.material_id, parsed.lot_no, parsed.qty, input.action);
  });

  return { success: true, remaining: await getRemaining(entry.id, parsed.material_id) };
}
```

## 5.5 剩余用量与可用时间预警

### 5.5.1 剩余数量计算
```text
剩余数量 = 上料累计数量 − 已消耗数量
上料累计数量 = Σ smt_feed_log.base_qty WHERE station_table_entry_id = ? AND action IN ('LOAD','RELOAD')
已消耗数量   = station_material_stock.qty_consumed（由工序汇报审核钩子扣减，见 E12）
```

### 5.5.2 消耗扣减规则（一期/二期差异）
- **一期（按报工扣减）**：工序汇报单（`sfc_report`）审核通过后，在 `afterAudit` 钩子中，按该工序计划行关联的 BOM（`pl_bom_entry`）分子/分母 × 报工合格数量（`ok_qty`），累加到 `station_material_stock.qty_consumed`，并同步扣减 `qty_remaining`。
- **二期（自动消耗）**：设备采集到实际投料信号（如贴片机吸嘴动作计数）实时扣减，不再依赖报工触发。

【依据:修订单 E12、需求说明书 8.4、技术方案 3.2.6 #153】

### 5.5.3 可用时间公式（原文口径）
> 可用时间 = 剩余数量 / ((分子用量/分母用量) × 对应工序计划行的单位加工活动量之和)，折算分钟

**符号定义**：
- `R` = 剩余数量（`qty_remaining`）
- `num/den` = BOM 分子用量 / 分母用量（`pl_bom_entry.numerator_qty / denominator_qty`）
- `A_i` = 第 i 条工序计划行的单位加工活动量（`sfc_op_plan_entry.unit_activity_qty`，即单位产量所需的标准工时/节拍，单位：分钟/件）
- 求和范围：当前正在排产/执行的、使用该工位物料的所有工序计划行（同一物料可能被多道工序共用）

**完整公式**：
```text
可用时间(分钟) = R / ( (num/den) × Σ A_i )
```


> 【核对】K11：若 `A_i` 是“分钟/件”，`R / ((num/den) × A)` 量纲不对。应为 可用分钟 = R ÷ (num/den × 每分钟产量) = R × A ÷ (num/den)；一期近似 = R × (理论节拍秒/60) ÷ (num/den)。原文“单位加工活动量”的确切含义待确认。

### 5.5.4 一期采用的近似算法
因一期暂无实时多工序并行排产的精确 `Σ A_i`，采用以下近似：
1. **理论节拍法（默认）**：取设备/工艺路线维护的理论节拍 `tact_time`（秒/件），换算为 `A = tact_time / 60`（分钟/件）。若该物料在多台设备/多条线并行，取**最小**节拍（最快消耗）以保守预警。
   ```text
   可用时间 ≈ R / ( (num/den) × (min_tact_time/60) )
   ```
2. **近 N 分钟实际速率法（可选配置）**：统计最近 `N` 分钟（默认 30 分钟）该工位/设备的实际产出速率 `v_actual`（件/分钟），则 `A_actual = 1 / v_actual`。
   ```text
   可用时间 ≈ R / ( (num/den) × A_actual )
   ```
   > 若 `v_actual = 0`（设备停机），回退到理论节拍法。

**配置参数**（`eqp_equipment` 扩展字段或 `smt_station_table` 维护）：
- `consumption_mode`: 'THEORETICAL' | 'ACTUAL_RATE'
- `actual_rate_window_min`: 30（仅 ACTUAL_RATE 生效）

### 5.5.5 预警触发与推送
- **判定条件**：`可用时间 ≤ 60 分钟` 且 `qty_remaining > 0`。
- **推送主题**：`station.material`（WebSocket 房间 `line:{lineId}` + `eqp:{eqpId}`）。

### 5.5.6 伪代码（预警扫描任务，每 1 分钟运行）
```typescript
async function scanStationMaterialWarning() {
  const stocks = await db.select('station_material_stock', {
    where: { qty_remaining: { '>': 0 }, is_active: 1 },
    join: ['smt_station_table_entry', 'pl_bom_entry', 'eqp_equipment']
  });

  for (const s of stocks) {
    const { remaining_qty, numerator_qty, denominator_qty, tact_time, consumption_mode } = s;
    const rate = numerator_qty / denominator_qty; // 单位产量消耗物料量

    let unitActivity; // 分钟/件
    if (consumption_mode === 'ACTUAL_RATE') {
      const v = await calcActualRate(s.station_id, s.equipment_id, 30); // 件/分钟
      unitActivity = v > 0 ? 1 / v : tact_time / 60;
    } else {
      unitActivity = tact_time / 60;
    }

    const availableMin = remaining_qty / (rate * unitActivity);

    if (availableMin <= 60) {
      await pushWarning(s, availableMin);
      if (availableMin <= 30 && orgParam.autoCreateMaterialAndon) {
        await createAndonTicket({ ...s, event_type: 'MATERIAL_SHORTAGE', level: 'LEVEL_1' });
      }
    }
  }
}
```

## 5.6 安灯升级与超时

### 5.6.1 扫描频率与升级触发
- **扫描周期**：每 1 分钟（由 `andon_escalation_scan` 定时任务触发）。
- **升级策略来源**：`eqp_event_escalation` 表，按 `event_type` + `org_id` + `level` 维护。
- **升级条件**：当前安灯单（`andon_ticket`）处于 `HANDLING` 状态，且距离上一次升级/创建时间 ≥ 当前等级对应的 `escalation_interval_min`。

### 5.6.2 等级升级规则
| 当前等级 | 升级后等级 | 升级间隔（分钟） | 通知对象扩展 |
|---|---|---|---|
| LEVEL_1 | LEVEL_2 | `eqp_event_escalation.interval_min` (L1→L2) | 增加班长/主管 |
| LEVEL_2 | LEVEL_3 | `eqp_event_escalation.interval_min` (L2→L3) | 增加车间主任/厂长 |
| LEVEL_3 | LEVEL_3（封顶） | — | 全员广播/短信 |

> 升级时：更新 `andon_ticket.current_level`、`escalated_at`、`escalated_by='SYSTEM'`；写入 `andon_step_log`（`step='ESCALATE'`）；重新计算 `andon_deadline` 三个截止时间。

### 5.6.3 预计关闭时间计算
> 预计关闭时间 = 发生时间 + 升级策略处理时长最小值

**公式**：
```text
预计关闭时间 = andon_ticket.occur_time + MIN( eqp_event_escalation.process_timeout_min )  // 取该事件类型所有等级中最小的处理时长
```
- `process_timeout_min` 字段在 `eqp_event_escalation` 维护，表示该等级允许的最大处理时长。
- 取最小值是为了给最紧的 SLA 预留缓冲，便于看板显示“倒计时”。

### 5.6.4 三类超时判定（依据 `andon_deadline` 表）
`andon_deadline` 每张安灯单生成/升级时重算三行：
| deadline_type | 截止时间计算 | 超时后动作 |
|---|---|---|
| ACCEPT（受理） | `occur_time + eqp_event_handler.accept_timeout_min` | 未受理 → 自动升级/派单给上级 |
| CHECKIN（签到/到场） | `accept_time + eqp_event_handler.checkin_timeout_min` | 未签到 → 升级/通知备选处理人 |
| RESOLVE（处理完成） | `accept_time + eqp_event_escalation.process_timeout_min`（当前等级对应） | 超时未关闭 → 升级/触发预防措施跟踪单 |

**判定逻辑（每分钟扫描）**：
```text
FOR each andon_ticket WHERE status='HANDLING':
  FOR each deadline IN andon_deadline WHERE ticket_id=... AND is_met=0:
    IF now() > deadline.due_time:
       deadline.is_met = 1 (超时标记)
       触发对应动作（升级/派单/生成预防措施跟踪单）
```

### 5.6.5 伪代码（升级与超时扫描合并任务）
```typescript
async function scanAndonEscalationAndTimeout() {
  const now = new Date();
  const tickets = await db.select('andon_ticket', {
    where: { status: 'HANDLING' },
    join: ['eqp_event_escalation', 'eqp_event_handler']
  });

  for (const t of tickets) {
    const esc = t.eqp_event_escalation; // 当前等级对应的升级策略行
    const hdl = t.eqp_event_handler;    // 处理人配置

    // 1. 等级升级判定
    const lastEscTime = t.escalated_at || t.occur_time;
    if (now.getTime() - lastEscTime.getTime() >= esc.interval_min * 60_000) {
      if (t.current_level !== 'LEVEL_3') {
        await escalateTicket(t, esc);
      }
      // 升级后重新计算 deadline
      await recalcDeadlines(t);
      continue; // 本轮不再做超时判定，下一分钟再扫
    }

    // 2. 三类超时判定
    const deadlines = await db.select('andon_deadline', { where: { ticket_id: t.id, is_met: 0 } });
    for (const dl of deadlines) {
      if (now > dl.due_time) {
        await handleDeadlineTimeout(t, dl, hdl, esc);
      }
    }
  }
}

async function escalateTicket(t, esc) {
  const nextLevel = levelUp(t.current_level); // LEVEL_1→2, 2→3
  await db.tx(async (tx) => {
    await tx.update('andon_ticket', t.id, {
      current_level: nextLevel,
      escalated_at: now,
      escalated_by: 'SYSTEM',
      handler_id: getNextLevelHandler(t.org_id, nextLevel, t.event_type)
    });
    await tx.insert('andon_step_log', {
      ticket_id: t.id, step: 'ESCALATE', from_level: t.current_level,
      to_level: nextLevel, operator_id: 'SYSTEM', remark: '自动升级'
    });
  });
}

async function recalcDeadlines(t) {
  const esc = await getEscalationRule(t.event_type, t.org_id, t.current_level);
  const hdl = await getHandlerConfig(t.event_type, t.org_id);
  const base = t.occur_time;
  const minProcess = await db.selectOne('eqp_event_escalation', {
    where: { event_type: t.event_type, org_id: t.org_id },
    aggregate: 'MIN(process_timeout_min)'
  });

  const deadlines = [
    { type: 'ACCEPT', due: addMin(base, hdl.accept_timeout_min) },
    { type: 'CHECKIN', due: t.accept_time ? addMin(t.accept_time, hdl.checkin_timeout_min) : null },
    { type: 'RESOLVE', due: addMin(t.accept_time || base, esc.process_timeout_min) },
    { type: 'EST_CLOSE', due: addMin(base, minProcess) } // 预计关闭时间
  ];

  await db.delete('andon_deadline', { ticket_id: t.id });
  await db.insertBatch('andon_deadline', deadlines.map(d => ({ ticket_id: t.id, ...d, is_met: 0 })));
}

async function handleDeadlineTimeout(t, dl, hdl, esc) {
  await db.update('andon_deadline', dl.id, { is_met: 1, met_at: now });
  switch (dl.type) {
    case 'ACCEPT':
      // 未受理：自动派单给上级处理人
      await reassignTicket(t, getNextLevelHandler(t.org_id, t.current_level, t.event_type));
      break;
    case 'CHECKIN':
      // 未签到：通知备选处理人/升级
      await notifyBackupHandlers(t);
      if (t.current_level !== 'LEVEL_3') await escalateTicket(t, esc);
      break;
    case 'RESOLVE':
      // 处理超时：升级 + 生成预防措施跟踪单（andon_prevent_track）
      if (t.current_level !== 'LEVEL_3') await escalateTicket(t, esc);
      await createPreventTrack(t, 'RESOLVE_TIMEOUT');
      break;
  }
}
```

### 5.6.6 边界条件
| 场景 | 处理 |
|---|---|
| 安灯单创建后立即被受理（`accept_time` 设定） | `CHECKIN` 与 `RESOLVE` 截止时间以 `accept_time` 为基准重算 |
| 处理人主动降级（不支持一期） | 一期不提供降级操作，仅升级；关闭单据即终止 |
| `accept_timeout_min = 0` | 视为无受理超时控制，跳过 ACCEPT deadline |
| 升级策略缺失（`eqp_event_escalation` 无对应行） | 使用组织级默认策略（`LEVEL_1: 10min, LEVEL_2: 20min, LEVEL_3: 30min`），记录配置缺失告警 |
| 设备离线/通讯中断期间 | 扫描任务仍按服务器时间运行，超时判定不因设备离线暂停 |
