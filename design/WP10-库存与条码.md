### 0.3 与《平台开发约定》V0.1 的对齐说明（人工核对）

约定文件：/workspace/erp-3d/fullsys/code/docs/平台开发约定.md（V0.1）。它是在本设计正文生成之后才发布的，所以正文没有参照它。下面是人工逐条比对后的结论；编码时以约定为准，正文没有据此改写。

1. **建表方式（约定 3.2、3.5、10.3）**：单据表不能手写 `CREATE TABLE`，要用 BillMeta 元数据（字段 snake_case）配合 `ensureBillTables` 在幂等迁移里建表；表头 25 个公共列、分录 18 个公共列（如 id、org_id、bill_no、status、close_status、src_form、src_entry_id、lot_no、qty、base_qty、biz_close 等）由框架自动加，元数据里不能再声明。所以第 1 节单据表的 DDL 只作为字段清单参考，实现时要改写成 BillMeta，并去掉公共列。非单据表（即时库存、流水、条码主档、国标抽样表等）在迁移里用 `ensureTable`、`addColumnIfMissing`、`addIndexIfMissing` 幂等建表；约定禁止 DROP，也禁止改已有列的类型。
2. **字段类型（约定 3.1）**：数量、金额统一用 DECIMAL(23,10)，datetime 用 DATETIME(3)，bool 用 TINYINT(1)，enum 用 VARCHAR(20)。正文里状态、枚举列宽度有 VARCHAR(16/32) 等写法，实现时按 FieldType 映射统一。
3. **状态维度取值（约定 5.1）**：close_status、cancel_status、forbid_status 一律用 `A` 正常、`B` 关闭/作废/禁用。正文 DDL 里出现的 OPEN/NORMAL/NO、0/1 都要改。作废不是主状态，是维度：正文状态机表中“to=作废”“已关闭”应理解为 cancel_status=B、close_status=B，主状态 status 不变。
4. **操作规则（约定 5.2）**：已审核单据必须先反审核才能作废；cancel 只允许从 CREATED、REAUDIT 发起；下游有有效单据时禁止反审核，错误码为 `BIZ_HAS_DOWNSTREAM`。正文与此冲突的地方以约定为准。
5. **钩子名（约定 2.2 BillHooks）**：已确认的钩子有 beforeSave、afterSave、beforeAudit、afterAudit、beforeUnaudit、afterUnaudit、beforeCancel、afterCancel、beforeDelete，以及行级 rowGuards。正文里标的“钩子名【待确认】”这些可以销项。正文用到的 `beforeSubmit` 不在约定列表里，要么并入 beforeSave、beforeAudit，要么请 WP02 增加。
6. **反写规则字段（约定 6.2 WritebackRuleConfig）**：约定中 `srcForm` 是**被反写的上游**单据，`tgtForm` 是**触发反写的下游**单据。正文反写表大多写成“下游→上游 = src_form→tgt_form”，方向正好相反，实现时要对调。`onEvent` 只有 `save` 和 `audit` 两个值，反审核、删除、作废的回滚由引擎按两段规则自动完成，不用单独配。正文里的 `unaudit`、`delete`、“质检完成”等事件不能直接配置：“质检完成”属于行级状态，需要用 RowStatusConfig 加 rowGuards，或者请 WP02 支持行状态事件触发反写，已列入待确认。`mode` 取值为 add、sub、overwrite（正文写的是累加、扣减、覆盖）；`overCtrl` 取值为 FORBID、ONCE、ALLOW（正文写的是禁止、允许一次、允许）；`closeScope` 取值为 ALL、ANY、NONE。
7. **转换规则字段（约定 6.1 ConvertRuleConfig）**：字段为 srcForm、tgtForm、srcStatus、srcQtyField、srcLinkField、header/entry 映射、groupBy、filterExpr、autoPushOnAudit。正文的 bill_type_map_json、field_map_json、group_json、auto_push 分别对应 header/entry、groupBy、autoPushOnAudit；自动下推统一用 `autoPushOnAudit`。
8. **两段反写（约定 6.5 第 3 条）**：保存时累加上游关联数量（释放发生在删除或作废时），审核时累加上游执行数量（反审核时冲减）。正文总体一致，个别段落用同一个字段先累加再扣减，见段内批注。
9. **事务与并发（约定 6.5）**：上游行按 id 升序 `SELECT … FOR UPDATE`；累加一律用增量 UPDATE；状态变更、反写、库存（scm_inventory、scm_inv_txn）、sys_bill_link 放在同一个 `DbService.tx` 事务里；outbox、WebSocket 用 `DbService.afterCommit` 在提交后发出。正文写的是“outbox 行在事务内写入、由 worker 发送”。约定 6.5 第 5 条的原话是“sys_event_outbox 触发事件必须通过 afterCommit 调度”，没说清 outbox 行能不能在事务内 INSERT，需要 WP02 确认，已列入待确认。
10. **接口（约定 4.1–4.4）**：标准单据的增删改查和操作统一走引擎的 `/api/v1/bills/{form}…`，正文第 4 节一致。列表参数是 page、size（默认 50，最大 500）、sort、filter（JSON）。响应统一为 `{code,msg,data,traceId,errors?}`，成功时 code='OK'，逐行错误放在 RowError（entity、row、field、msg）。正文的专用接口（扫码、AQL 计算、查询报表等）也要套这个响应外壳。

### 0.4 本轮实现裁决（2026-11-18）

以下裁决覆盖正文及测试用例中相冲突的旧描述：

1. 库存状态变化（请检冻结、检验判定、MSL 超时冻结/烘烤解冻等）只能生成并审核 D46 `scm_status_convert`，不得直接改 `scm_inventory` 或用 `lock_qty` 代替库存状态。

### 1. 库存核心表 MySQL 8 建表 DDL

#### 1.1 scm_inventory（即时库存）

用途：按库存维度记录实时库存数量，是 WP10 所有库存更新的唯一事实来源；对应 D42–D50 单据审核时由库存服务更新（E02 批号贯穿、P10 G2 §4 库存维度）。唯一键覆盖材料规定的 15 个库存维度，采用「维度列全部 NOT NULL + 空值用 0 / '' 占位 + 哈希校验列」方案落地（见下方说明）。

MySQL 唯一索引最多 16 列且 NULL 不参与唯一性比较，材料要求的库存维度为 15 个（物料、辅助属性、批号、生产日期、有效期至、BOM 版本、计划跟踪号、库存状态、货主类型、货主、保管者类型、保管者、仓库、仓位，加 org = 15 列），若任一维度允许 NULL 则同一维度组合会出现重复行。因此所有维度列 NOT NULL，无值时以 0（数值外键）或 ''（字符串）占位；另增加 `dim_hash`（维度组合的 SHA2 哈希）作为第 16 列唯一键成员，双重保障唯一性并缩短索引长度。「建议」

```sql
CREATE TABLE scm_inventory (
  id              BIGINT       NOT NULL COMMENT '主键(雪花)',
  org_id          BIGINT       NOT NULL COMMENT '组织【Q02 单组织预留】',
  material_id     BIGINT       NOT NULL COMMENT '物料',
  aux_prop_id     BIGINT       NOT NULL DEFAULT 0 COMMENT '辅助属性(无则 0)',
  lot_no          VARCHAR(64)  NOT NULL DEFAULT '' COMMENT '批号(E02 批号贯穿; 无则空串)',
  prod_date       DATE         NOT NULL DEFAULT '1970-01-01' COMMENT '生产日期(D/C 换算后存放 E04)',
  exp_date        DATE         NOT NULL DEFAULT '1970-01-01' COMMENT '有效期至(无则哨兵日期)',
  bom_id          BIGINT       NOT NULL DEFAULT 0 COMMENT 'BOM 版本(无则 0)',
  mto_no          VARCHAR(64)  NOT NULL DEFAULT '' COMMENT '计划跟踪号(无则空串)',
  stock_status_id BIGINT       NOT NULL DEFAULT 0 COMMENT '库存状态(B12)',
  owner_type      VARCHAR(16)  NOT NULL DEFAULT '' COMMENT '货主类型',
  owner_id        BIGINT       NOT NULL DEFAULT 0 COMMENT '货主',
  keeper_type     VARCHAR(16)  NOT NULL DEFAULT '' COMMENT '保管者类型',
  keeper_id       BIGINT       NOT NULL DEFAULT 0 COMMENT '保管者',
  warehouse_id    BIGINT       NOT NULL DEFAULT 0 COMMENT '仓库(B11)',
  location_id     BIGINT       NOT NULL DEFAULT 0 COMMENT '仓位(无则 0)',
  dim_hash        CHAR(64)     NOT NULL COMMENT '维度组合 SHA2 哈希, 唯一键成员「建议」',
  qty             DECIMAL(23,10) NOT NULL DEFAULT 0 COMMENT '现存数量(基本单位)',
  base_qty        DECIMAL(23,10) NOT NULL DEFAULT 0 COMMENT '基本单位数量',
  lock_qty        DECIMAL(23,10) NOT NULL DEFAULT 0 COMMENT '预留占用数量，不表达库存状态冻结',
  version         INT          NOT NULL DEFAULT 0 COMMENT '乐观锁',
  created_at      DATETIME(3)  NOT NULL,
  modified_at     DATETIME(3)  NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_inventory_dim (org_id, material_id, aux_prop_id, lot_no, prod_date, exp_date,
                               bom_id, mto_no, stock_status_id, owner_type, owner_id,
                               keeper_type, keeper_id, warehouse_id, location_id, dim_hash),
  KEY idx_material (material_id),
  KEY idx_lot (lot_no),
  KEY idx_status_wh (stock_status_id, warehouse_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='即时库存(按库存维度)';
```

> 【核对:qty 与 base_qty 两列同为“基本单位数量”，语义重复；技术方案 175 行只列 qty, lock_qty, base_qty，建议明确 qty 为库存单位、base_qty 为基本单位，或去掉一列。另：头表/行表公共列 close_status、cancel_status 的取值在 code/packages/shared/src/status.ts 已定为 A/B，本设计各表写的是 OPEN/NORMAL 等，需统一。】

#### 1.2 scm_inv_txn（库存流水）

用途：库存单据每次审核批次按分录记录方向、基本数量、发生后结存。流水只追加、不删除；反审核读取尚未冲回的审核批次，按原始流水逐条追加方向相反的流水（D42–D50、R41）。唯一键固定为 `uk_txn_idem (form, bill_id, entry_id, direction, audit_batch)`；`audit_batch` 在同一单据头每次重新审核时递增，`direction` 为 `IN` / `OUT` / `REV_IN` / `REV_OUT`。

```sql
CREATE TABLE scm_inv_txn (
  id            BIGINT       NOT NULL COMMENT '主键(雪花)',
  org_id        BIGINT       NOT NULL COMMENT '组织',
  inventory_id  BIGINT       NOT NULL COMMENT 'scm_inventory.id',
  form          VARCHAR(32)  NOT NULL COMMENT '来源单据 form(Z 节: scm_other_in 等)',
  bill_id       BIGINT       NOT NULL COMMENT '来源单据头 id',
  entry_id      BIGINT       NOT NULL COMMENT '来源单据行 id',
  direction     VARCHAR(20)  NOT NULL COMMENT '动作方向: IN/OUT/REV_IN/REV_OUT',
  base_qty      DECIMAL(23,10) NOT NULL COMMENT '基本单位数量（非负；方向决定增减）',
  balance_after DECIMAL(23,10) NOT NULL COMMENT '发生后结存(基本单位)',
  audit_batch   INT          NOT NULL COMMENT '单据头审核批次；重审递增',
  reversal_of   BIGINT       NULL COMMENT '反向流水对应的原流水ID',
  op            VARCHAR(16)  NOT NULL COMMENT '操作: AUDIT / UNAUDIT',
  operator_id   BIGINT       NOT NULL COMMENT '操作人',
  at            DATETIME(3)  NOT NULL COMMENT '发生时间',
  PRIMARY KEY (id),
  UNIQUE KEY uk_txn_idem (form, bill_id, entry_id, direction, audit_batch),
  KEY idx_bill (form, bill_id),
  KEY idx_inventory (inventory_id),
  KEY idx_at (at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='库存流水';
```

#### 2.3 审核/反审核钩子与库存服务调用明细（引擎事务内）

| 操作 | 钩子 | 库存服务调用（WP10 库存服务接口，事务内） | 反写 |

| audit（D45 直接调拨） |同上| `inventoryService.transfer(outKey, inKey, base_qty)`：调出扣减 + 调入增加，两条 scm_inv_txn | 无上游反写时为空配置 |

「建议」：库存服务接口由 WP10 提供，其他模块（采购/销售/生产/质量）只在自己的审核钩子里远程调用，不直接写 scm_inventory / scm_inv_txn（F 节硬约束）；
「建议」：钩子命名 beforeSave/afterSave/beforeSubmit/beforeAudit/afterAudit/beforeUnaudit/afterUnaudit/beforeDelete/beforeCancel 须与 WP02 平台开发约定对齐【待确认：钩子接口签名与注册方式以 WP02 发布为准】。

### 5. 库存更新与并发控制方案（不超卖、不重复扣减）

#### 5.1 库存服务的唯一入口与事务内调用顺序

库存表（`scm_inventory`、`scm_inv_txn`）只能由 WP10 库存服务更新，其他模块在单据审核钩子里调用本服务接口，不得直接写库存表【来源:F 节硬约束】。

```typescript
// 库存服务唯一入口（WP10 内部服务，非 REST）
// 调用方：单据引擎审核/反审核钩子（bill-engine 回调），在同一 DB 事务内执行
interface InventoryService {
  /**
   * 审核时更新库存（库存更新时机=审核时，组织参数，见材料 A、P10）
   * @param req 每行库存变更：库存维度键 + base_qty（基本单位，材料 A：数量一律按基本单位换算）
   */
  applyOnAudit(tx: Tx, req: AuditInvRequest): Promise<void>;

  /** 反审核：按 scm_inv_txn 流水逐条冲回，不按当前单据重新计算 */
  reverseOnUnaudit(tx: Tx, form: string, billId: bigint): Promise<void>;
}

interface AuditInvRequest {
  form: string;            // 单据 form，如 scm_other_out / pp_pick / scm_sal_outstock（Z 节）
  billId: bigint;
  entries: Array<{
    entryId: bigint;
    direction: 'IN' | 'OUT';
    // 库存维度（scm_inventory 唯一键，材料 B/L175）
    materialId: bigint;
    auxPropId?: bigint;
    lotNo?: string;
    prodDate?: Date;
    expDate?: Date;
    bomId?: bigint;
    mtoNo?: string;
    stockStatusId: bigint;
    ownerType?: string;
    ownerId?: bigint;
    keeperType?: string;
    keeperId?: bigint;
    warehouseId: bigint;
    locationId?: bigint;
    baseQty: Decimal;      // DECIMAL(23,10)，已按基本单位换算，材料 B
  }>;
}
```

#### 5.2 不超卖：扣减 SQL 与加锁顺序

原则：多行按库存主键升序加锁，避免死锁（材料 C 2.3："上游行按主键顺序加锁，避免死锁"）；出库扣减用"乐观版本 + 条件影响行数"双保险。

```sql
-- 出库扣减（不允许负库存仓库）：条件更新 + 影响行数校验
UPDATE scm_inventory
SET qty = qty - ?,
    base_qty = base_qty - ?,
    version = version + 1
WHERE id = ?
  AND qty - lock_qty >= ?          -- 可用数量 = qty - lock_qty（锁库占用，见 5.4）
  AND version = ?;                  -- 乐观锁
-- 若 ROW_COUNT() = 0：读取该行判定原因（行不存在 / 版本冲突 / 可用不足），抛 BIZ_INV_INSUFFICIENT 或 BIZ_INV_CONFLICT
```

允许负库存仓库（B11 `allow_negative = 1`）分支：跳过 `qty - lock_qty >= ?` 条件，但仍保留 `version` 乐观锁：

```sql
UPDATE scm_inventory
SET qty = qty - ?, base_qty = base_qty - ?, version = version + 1
WHERE id = ? AND version = ?;
```

入库增加（幂等前置：先查是否已存在该流水，见 5.3）：

```sql
UPDATE scm_inventory
SET qty = qty + ?, base_qty = base_qty + ?, version = version + 1
WHERE id = ? AND version = ?;
-- 行不存在时（新库存维度首次入库）：INSERT ... ON DUPLICATE KEY UPDATE qty = qty + VALUES(qty)
```

完整事务内伪代码（按主键升序加锁）：

```typescript
async function applyOnAudit(tx: Tx, req: AuditInvRequest) {
  // 1. 幂等前置：该单据是否已写过流水（防重复提交/重试）
  const exist = await tx.query(
    `SELECT 1 FROM scm_inv_txn WHERE form = ? AND bill_id = ? LIMIT 1`, [req.form, req.billId]);
  if (exist.length) throw biz('BIZ_INV_DUPLICATE_TXN');

  // 2. 库存维度键聚合（同一维度同方向合并，减少锁行数）
  const agg = aggregateByInvKey(req.entries);

  // 3. 先 SELECT ... FOR UPDATE 按 id 升序锁定（与 C 2.3 "按主键顺序加锁" 一致）
  const ids = agg.map(a => a.invId).filter(Boolean).sort((a, b) => a - b);
  // invId 未知时先按唯一键查出 id
  const rows = await tx.query(
    `SELECT id, qty, lock_qty, version, warehouse_id FROM scm_inventory
     WHERE id IN (?) ORDER BY id FOR UPDATE`, [ids]);

  // 4. 逐行扣减/增加，检查影响行数
  for (const a of agg) {
    const wh = await getWarehouse(a.warehouseId); // scm_warehouse.allow_negative，B11
    let sql, params;
    if (a.direction === 'OUT') {
      if (wh.allow_negative) {
        sql = `UPDATE scm_inventory SET qty = qty - ?, base_qty = base_qty - ?, version = version + 1
               WHERE id = ? AND version = ?`;
      } else {
        sql = `UPDATE scm_inventory SET qty = qty - ?, base_qty = base_qty - ?, version = version + 1
               WHERE id = ? AND qty - lock_qty >= ? AND version = ?`;
      }
    } else { /* IN */ }
    const r = await tx.execute(sql, params);
    if (r.affectedRows === 0) {
      const cur = rows.find(x => x.id === a.invId);
      throw biz(cur && cur.qty - cur.lock_qty < a.baseQty ? 'BIZ_INV_INSUFFICIENT' : 'BIZ_INV_CONFLICT');
    }
    // 5. 写流水（幂等唯一键）
    await tx.execute(
      `INSERT INTO scm_inv_txn (inventory_id, form, bill_id, entry_id, direction, base_qty, at)
       VALUES (?, ?, ?, ?, ?, ?, NOW(3))`, [a.invId, req.form, req.billId, a.entryId, a.direction, a.baseQty]);
  }
}
```

`scm_inv_txn` 唯一键固定为 `UNIQUE KEY uk_txn_idem (form, bill_id, entry_id, direction, audit_batch)`。

> 【本轮修正：审核流水、反审核冲销流水均永久保留；唯一键含单据审核批次及动作方向。不得删除流水，也不得为复用唯一键覆盖旧记录。】


#### 5.3 不重复扣减：四层防护

| 层 | 机制 | 落点 |
|---|---|---|
| 1 | `scm_inv_txn` 幂等唯一键 `(form, bill_id, entry_id, direction, audit_batch)`，重复 INSERT 直接失败回滚 | 本节裁决 |
| 2 | 单据状态前置校验：状态机（`sys_state_machine`）保证只有"审核中"才能执行 `audit`；已审核单不能重复审核 | 材料 C 2.3、H SM-01 |
| 3 | `Idempotency-Key` 请求头写入 `sys_idempotent_key`，PDA 弱网重复提交直接返回首次结果 | 材料 E 4.1 + D36【建议】 |
| 4 | 网络互斥：编辑/操作前占 `sys_bill_lock`（object_id, bill_id, user_id, locked_at），同单同一时刻单人操作 | 材料 D36 |

反审核冲回按该单据最新且未冲回的审核批次逐条处理（不得重新读取当前单据分录推算，也不得删除原流水）：

```sql
-- 召回方向与原流水相反，逐条冲回
SELECT id, inventory_id, direction, base_qty, entry_id, audit_batch FROM scm_inv_txn
WHERE form = ? AND bill_id = ? AND audit_batch = ? AND direction IN ('IN', 'OUT') ORDER BY id FOR UPDATE;

-- 对每条：IN → REV_OUT，OUT → REV_IN；更新库存与追加反向流水处于同一事务
UPDATE scm_inventory SET qty = qty + ?, base_qty = base_qty + ?, version = version + 1
WHERE id = ? AND version = ?;   -- 冲回也走条件更新 + 乐观锁

INSERT INTO scm_inv_txn (..., direction, audit_batch, reversal_of, ...)
VALUES (..., ?, ?, ?, ...); -- 只追加，不更新或删除任何历史流水
```

【来源:H】有下游有效单据时禁止反审核（`sys_bill_link` 查下游），盘盈/盘亏单（D49/D50）不能反审核——由状态机前置条件拦截。

#### 5.4 锁库 lock_qty 的占用与释放

`lock_qty` 只表达预留占用，不表达冻结；请检、质检、MSL 引起的冻结统一走 D46 状态转换。D46 审核将数量从源库存状态转至目标状态，因此冻结库存天然不再计入可用状态，不需要同步调整 `lock_qty`。

> 【本轮修正：请检冻结经 D46 库存状态转换实现；lock_qty 仅用于其他业务选单预留。】


锁库条件：仓库与库存状态都"可锁库"——`scm_warehouse` 启用 + `scm_stock_status.can_lock = 1`（B11/B12，材料 L172/L174）。

```sql
-- 占用（例如发货请检审核后自动冻结/锁库，R35：请检审核后自动冻结库存）
UPDATE scm_inventory SET lock_qty = lock_qty + ?, version = version + 1
WHERE id = ? AND version = ?
  AND EXISTS (SELECT 1 FROM scm_stock_status s WHERE s.id = scm_inventory.stock_status_id AND s.can_lock = 1);

-- 释放（检验完成、状态转换单审核后解锁）
UPDATE scm_inventory SET lock_qty = lock_qty - ?, version = version + 1
WHERE id = ? AND lock_qty >= ? AND version = ?;
```

可用数量口径恒为 `qty - lock_qty`（5.2 扣减条件即体现）。

#### 5.5 卷盘码与即时库存的一致性

卷盘码（Reel ID）不作为库存维度，挂在"物料 + 批号 + 仓库 + 仓位"下的条码主档（E01，材料 N、P10）【扩展】；一致性口径：

```

  = scm_inventory.qty 对应行（同 物料+批号+仓库+仓位+库存状态）
```

#### 5.7 高并发场景处理

- **PDA 批量扫码**：所有写操作带 `Idempotency-Key`（材料 E），服务端写 `sys_idempotent_key` 唯一键去重；批量操作接口 `POST /bills/{form}/batch-ops/{op}` 逐单返回 `results:[{id, ok, msg}]`（材料 E），单单独立事务，互不影响。
- **同一卷盘被两台 PDA 同时扫**：卷盘扣减落在同一行 `bc_barcode_master` + 同一行 `scm_inventory`，走 5.2 条件 UPDATE（`qty - lock_qty >= ? AND version = ?`）+ 影响行数校验，先到先得，后到的返回 `BIZ_INV_INSUFFICIENT` 或 `BIZ_INV_CONFLICT` 并整单回滚；`sys_bill_lock` 保证同一张领料/出库单不会被两人同时编辑（材料 D36）。卷盘拆分（D51）主码扣减同样走条件更新，拆出子码为 `主码-流水号`（材料 L226-227）。
- 高频反写用增量 UPDATE（材料 C 2.3），消息/财务事件写 `sys_event_outbox` 由 worker 发送，保证不丢不重【建议】。
- MSL 超时冻结（SM-14，材料 M10【扩展】）：超时后自动生成库存状态转换单（D46）转为"冻结"，经单据引擎审核事务走库存服务，不直接改库存表【来源:F】。

##### 5.2.1.2 暴露计时公式

状态定义见 SM-14：密封 → 已开封 →（回柜/真空包装 → 密封，暂停计时「建议」）→ 超时冻结 → 烘烤中 → 密封（清零）。

```python
# 伪代码：计算卷盘当前累计暴露（分钟）与剩余寿命
def calc_exposure(barcode_row, now: datetime) -> (exposed_min: int, remain_min: int, floor_life_min: int):
    floor_life_min = barcode_row.floor_life_h * 60          # 车间寿命（分钟）
    if barcode_row.msl_status == '密封':
        return 0, floor_life_min, floor_life_min
    if barcode_row.msl_status == '已开封':
        # 累计暴露 = 历史累计 + 本次开封后未暂停的时长
        exposed = barcode_row.exposed_min + int((now - barcode_row.last_open_at).total_seconds() // 60)
    elif barcode_row.msl_status == '超时冻结':
        exposed = barcode_row.exposed_min                     # 已冻结，不再计时
    elif barcode_row.msl_status == '烘烤中':
        exposed = barcode_row.exposed_min                     # 烘烤中不计入暴露
    else:
        exposed = barcode_row.exposed_min
    remain = floor_life_min - exposed
    return exposed, remain, floor_life_min
```

- 回干燥柜/真空包装时暂停计时的落地方式「建议」：在 `bc_msl_log` 记录 `回柜` 事件，并把 `last_open_at` 到该时刻的时长累加进 `exposed_min`，同时将 `msl_status` 置回 `密封`、清空 `last_open_at`；重新开封时重新写 `last_open_at`。这样公式无需改动，SM-14 的「暂停计时」即等价于重新密封。

#### 5.2.2 D/C（日期码）换算与校验（E04、Q16）

Q16 已确认：客户 D/C 按 ISO 8601 周（YYWW；周一为一周第一天，YY 为 ISO 周年）。

```python
# 伪代码：来料 D/C(YYWW) → 生产日期 prod_date
def dc_to_prod_date(dc_yyww: str) -> date:
    # dc_yyww 格式 YYWW，如 "2647" = 2026 年第 47 周
    yy, ww = int(dc_yyww[:2]), int(dc_yyww[2:])
    year = 2000 + yy
    return date.fromisocalendar(year, ww, 1)   # ISO 8601：该周周一；非法周数直接拒绝

# 界面显示：prod_date 存储为日期，前端按同一规则反算 YYWW 展示
def prod_date_to_dc(d: date) -> str:
    iso = d.isocalendar()
    return f"{iso[0] % 100:02d}{iso[1]:02d}"
```

- 来料：收料通知单（scm_receive）扫描供应商标签解析出 D/C，经 `dc_to_prod_date` 写入 `scm_receive_entry.prod_date`，并随批号主档 `scm_lot_master.prod_date` 贯穿（E02），界面同时显示 YYWW（E04）。
- 销售订单行 `scm_sal_order_entry.dc_not_before`（YYWW 存储，建议存原始 YYWW 字符串避免换算歧义）：

#### 5.2.3 先进先出（FIFO）校验（E05）

参数（P10 第 7 节）：先进先出条码控制 = 严格控制，控制维度 = 物料 + 批号 + 仓库；拣货规则 = 顺序出库-入库日期 或 近效期先出。

```sql
-- 推荐候选列表 SQL（PDA 扫码推荐 / 校验基准）
-- 规则 A：顺序出库-入库日期（默认）
SELECT b.barcode, b.lot_no, l.in_date, b.qty, b.location_id
FROM bc_barcode_master b
JOIN scm_lot_master l ON l.org_id = b.org_id AND l.material_id = b.material_id AND l.lot_no = b.lot_no
WHERE b.org_id = :org_id
  AND b.material_id = :material_id
  AND b.lot_no = :lot_no                    -- 控制维度：物料+批号+仓库
  AND b.warehouse_id = :warehouse_id        -- 仓库维度（bc_barcode_master 需仓库字段，见 scm_inventory 维度回填【来源:扫描配置】）
  AND b.status = '入库'
  AND b.msl_status <> '超时冻结'             -- MSL 冻结卷盘不参与推荐
ORDER BY l.in_date ASC, b.barcode ASC       -- 最早入库日期优先
LIMIT 20;

-- 规则 B：近效期先出
--同上，ORDER BY l.exp_date ASC, l.in_date ASC
```

> 【核对:WHERE 里把批号固定成一个值，候选卷盘就全是同一批号，入库日期相同，按 in_date 排序起不到先进先出的作用。“控制维度 物料+批号+仓库”在原文里的含义需要回查金蝶“条码管理系统参数”页；更合理的做法可能是在“物料+仓库”范围内按批号的入库日期排序。已列入待确认。】


```python
# 伪代码：PDA 扫码出库/领料时的 FIFO 严格控制（E05）
def fifo_check(org_id, material_id, lot_no, warehouse_id, scanned_barcode, rule: str, allow_override_auth: bool):
    candidates = query_recommended_list(org_id, material_id, lot_no, warehouse_id, rule)  # 上面 SQL
    if not candidates: return
    earliest = candidates[0].barcode          # 最早入库日期（或近效期）的卷盘
    if scanned_barcode == earliest:
        return                                # 放行
    # 不是最早的卷盘
    if allow_override_auth and current_user_has_auth('FIFO_OVERRIDE'):
        log_override(scanned_barcode, user)   # 记录 bc_scan_log，op='FIFO授权出库'【扩展】
        return
    raise BizError('BIZ_FIFO_NOT_EARLIEST',
        f'严格FIFO：应先出 {earliest}（入库日期最早），扫描的是 {scanned_barcode}，拒绝或申请授权')
```

- 「严格控制」下未授权扫描非最早卷盘 → 拒绝并写 `bc_scan_log`（op='FIFO拒绝'）；授权路径【待确认】走工作流还是角色权限，材料未给依据，「建议」先走角色权限 `FIFO_OVERRIDE`。
- 控制维度中「仓库」落在条码主档上：`bc_barcode_master` 需 `warehouse_id` 字段（P10 4 节：扫描时仓库、仓位回填【来源:扫描配置】），若技术方案未列该列则「建议」新增。
