### 2.2 业务模块注册 API（WP02 待提供）
各业务模块在自身的 NestJS Module 的 `onModuleInit` 阶段，通过依赖注入 `BillEngineRegistry`，统一向单据引擎注册所辖的单据元数据、专有状态机、钩子逻辑、下推转换规则及反写规则。严禁业务模块自行编写通用 CRUD 或绕开引擎直接执行 UPDATE 改写单据主状态：

```typescript
// 约定类型：apps/api/src/bill-engine/bill-engine.registry.ts（待 WP02 新增）
import { Injectable, OnModuleInit } from '@nestjs/common';
import { BillMeta, StateMachineConfig, ConvertRuleConfig, WritebackRuleConfig } from '@erp3d/shared';
import { DbService } from '../db/db.service';
import { AuthUser } from '../common/request-context';

export interface BillHookContext {
  billId: number;
  header: Record<string, unknown>;
  entries: Record<string, unknown>[];
  user: AuthUser;
  db: DbService; // 当前事务上下文
  extra?: unknown;
}

export interface BillHooks {
  /** 保存前校验：可阻断保存并抛出 BizError */
  beforeSave?: (ctx: BillHookContext, mode: 'draft' | 'save') => Promise<void>;
  /** 保存后联动：处于同一事务内 */
  afterSave?: (ctx: BillHookContext, mode: 'draft' | 'save') => Promise<void>;
  /** 审核前校验：前置条件拦截 */
  beforeAudit?: (ctx: BillHookContext) => Promise<void>;
  /** 审核后联动：更新库存、触发后续事务内计算 */
  afterAudit?: (ctx: BillHookContext) => Promise<void>;
  /** 反审核前校验：下游占用、结账校验 */
  beforeUnaudit?: (ctx: BillHookContext) => Promise<void>;
  /** 反审核后联动：回滚库存 */
  afterUnaudit?: (ctx: BillHookContext) => Promise<void>;
  /** 作废前校验 */
  beforeCancel?: (ctx: BillHookContext) => Promise<void>;
  /** 作废后联动 */
  afterCancel?: (ctx: BillHookContext) => Promise<void>;
  /** 删除前校验 */
  beforeDelete?: (ctx: { billId: number; user: AuthUser; db: DbService }) => Promise<void>;
  /** 行级状态流转守卫（RowTransition.hook） */
  rowGuards?: Record<string, (entry: Record<string, unknown>, ctx: BillHookContext) => Promise<void>>;
}

export interface RegisterBillOptions {
  meta: BillMeta;
  stateMachine?: StateMachineConfig; // 不提供则使用默认 STD 状态机
  hooks?: BillHooks;
  converts?: ConvertRuleConfig[];     // 从本单下推的目标转换规则
  writebacks?: WritebackRuleConfig[]; // 由本单触发的上游反写规则
}
```

业务模块（如 `ScmModule`）的标准装配示例：
```typescript
import { Module, OnModuleInit } from '@nestjs/common';
import { BillEngineRegistry } from '../bill-engine/bill-engine.registry';
import { SCM_PUR_REQ_META } from './metas/scm_pur_req.meta';
import { PurReqHooks } from './hooks/pur_req.hooks';
import { RULE_PUR_REQ_TO_PUR_ORDER } from './rules/pur_req_to_pur_order.rule';
import { WB_PUR_REQ_ORDER_QTY } from './rules/wb_pur_req_order_qty.rule';

@Module({
  providers: [PurReqHooks],
})
export class ScmModule implements OnModuleInit {
  constructor(
    private registry: BillEngineRegistry,
    private purReqHooks: PurReqHooks,
  ) {}

  onModuleInit() {
    this.registry.registerBill({
      meta: SCM_PUR_REQ_META,
      // 使用默认 STD 状态机，无需传 stateMachine
      hooks: this.purReqHooks,
      converts: [RULE_PUR_REQ_TO_PUR_ORDER],
      writebacks: [WB_PUR_REQ_ORDER_QTY],
    });
  }
}
```

### 2.3 全局过滤器、拦截器与上下文
平台底层已封装三个核心拦截部件，全部挂载于 `apps/api/src/common/`：
1. **[ResponseInterceptor](apps/api/src/common/response.interceptor.ts)**：
   - 作用：全局拦截成功请求，自动解包并封装为统一响应体 `{ code: 'OK', msg: '', data, traceId }`。
   - 特例：若返回对象被标记 `RAW_RESPONSE`（如二进制导出 StreamableFile、图片流），拦截器直接穿透，不进行 JSON 包装。
2. **[AllExceptionsFilter](apps/api/src/common/exception.filter.ts)**：
   - 作用：全局捕获异常。识别 `BizError`、`ExprError`、NestJS `HttpException` 及 MySQL 驱动异常 `ER_DUP_ENTRY`。
   - 响应格式：自动填充 `traceId`，映射标准 HTTP 状态码，输出 `{ code, msg, data, traceId, errors? }`。
3. **[request-context.ts](apps/api/src/common/request-context.ts)**：
   - 基于 Node.js `AsyncLocalStorage` 封装全局上下文 `reqCtx`。
   - 【待 WP01 新增】入口中间件：为每个请求生成 `traceId` 并 `reqCtx.run()`，鉴权守卫解析 JWT 后写入 `AuthUser`（现有代码只有 `reqCtx` 定义和 `currentTraceId()` 读取，中间件和守卫尚未实现）。
   - 业务代码中任意深度调用 `currentCtx()`、`currentUser()`、`currentTraceId()`，严禁通过层层传参传递用户与链路追踪标识。后台定时任务与迁移使用预置的 `SYSTEM_USER`。

## 3. 单据元数据定义格式

> **状态**：类型已实现（[packages/shared/src/bill-meta.ts](packages/shared/src/bill-meta.ts)）；DDL 幂等生成器已实现（[apps/api/src/db/ddl.ts](apps/api/src/db/ddl.ts)）。

### 3.1 `FieldType` 与 MySQL 列映射规范
元数据中定义的 `FieldType` 经由 [ddl.ts:columnSql](apps/api/src/db/ddl.ts) 转换为 MySQL 物理列。业务开发定义字段时严禁脱离下表范围：

| `FieldType` | MySQL 8 物理列类型 | 默认列约束与说明 | 适用业务场景 |
|---|---|---|---|
| `string` | `VARCHAR(length)` | 默认 `length=100`，允许 NULL | 编码、文本标识、短描述 |
| `text` | `TEXT` | 允许 NULL，不设默认值 | 长备注、大段说明、位号清单 |
| `int` | `INT` | 允许 NULL（`columnSql` 只对 decimal/qty/price/amount/rate/bool 加 `NOT NULL DEFAULT 0`） | 排序、行号、版本号、天数 |
| `bigint` | `BIGINT` | 默认 NULL | 外部大整数（非外键引用） |
| `decimal` | `DECIMAL(23,10)` | 默认 `NOT NULL DEFAULT 0` | 纯通用高精度小数 |
| `qty` | `DECIMAL(23,10)` | 默认 `NOT NULL DEFAULT 0` | 业务数量、基本单位数量、实发数 |
| `price` | `DECIMAL(23,10)` | 默认 `NOT NULL DEFAULT 0` | 含税单价、不含税单价、核算成本 |
| `amount` | `DECIMAL(23,10)` | 默认 `NOT NULL DEFAULT 0` | 价税合计、金额、折后金额 |
| `rate` | `DECIMAL(23,10)` | 默认 `NOT NULL DEFAULT 0` | 税率、损耗率（%）、折现率 |
| `date` | `DATE` | 允许 NULL | 单据日期、交期、业务生效日 |
| `datetime` | `DATETIME(3)` | 允许 NULL（毫秒精度） | 审核时间、扫码操作时间戳 |
| `bool` | `TINYINT(1)` | `NOT NULL DEFAULT 0` | 是否赠品、紧急放行标识 |
| `ref` | `BIGINT` | 允许 NULL；自动建普通索引 `ix_{key}` | 外键引用对象 ID（`ref` 属性必填） |
| `enum` | `VARCHAR(length)` | 默认 `length=20`，NULL | 枚举代码值（`enum` 选项数组必填） |
| `json` | `JSON` | 允许 NULL，不设默认值 | 动态参数、组合属性快照 |

> 有 `default` 时：数值和 bool 为 `NOT NULL DEFAULT 值`，其它类型为 `NULL DEFAULT 值`（text/json 不设默认值）。

> **字段命名硬性要求**：所有字段 `key` 必须严格使用 `snake_case`（下划线命名法），它既是 MySQL 列名，也是 RESTful 接口出入参的标准属性名。

### 3.2 表公共列规范（禁止在元数据中重复声明）

### 3.3 字段属性约束说明
- `required?: boolean`：界面与保存时必录（暂存 `mode=draft` 时跳过校验）。
- `unique?: boolean`：表头字段在同组织（`org_id`）内唯一性校验。
- `index?: boolean`：自动为该物理列创建普通索引。
- `ref?: string`：引用目标业务对象代码（如 `'md_material'`、`'sys_user'`），支持 F8 弹窗选择。
- `enum?: { value: string; label: string }[]`：预置固定枚举选项。
- `sensitive?: boolean`：标记敏感字段（单价、金额、成本）。字段权限体系默认将其纳入受控字段管理。
- `readonly?: boolean`：系统级维护字段（如累计关联数量、执行数量、审核时间）。接口接收到该字段时直接丢弃，禁止前端传入篡改。

### 4.5 序列化约定与数据类型处理
依据 [apps/api/src/db/data-source.ts](apps/api/src/db/data-source.ts) 的数据库驱动连接配置，全栈通信数据类型做如下硬性约定：
1. **主键与外键 ID（BIGINT）**：
   - 驱动配置 `supportBigNumbers: true, bigNumberStrings: false`。
   - 系统生成的所有主键 ID 均为 **53 位安全雪花数字**（最大值 `< 2^53 - 1 = 9007199254740991`）。在 JSON 传输中**保持为数字（number）类型**，前端 JavaScript 可直接以安全数值进行运算与绑定，无需作为字符串强制转换。
2. **高精度数值（DECIMAL / qty / price / amount / rate）**：
   - 驱动配置 `decimalNumbers: false`。
   - 所有数据库 `DECIMAL(23,10)` 字段在查询时**严格返回字符串（string）**（例如 `"125.5000000000"`）。后端计算强制使用 `Decimal.js`（已在 `@erp3d/shared` 导出），严禁直接使用 JS `+ - * /` 浮点计算；前端渲染时按需截断显示。
3. **日期时间（DATE / DATETIME）**：
   - 驱动配置 `dateStrings: true`。
   - `DATE` 类型序列化为 `'YYYY-MM-DD'`；`DATETIME(3)` 序列化为 `'YYYY-MM-DD HH:mm:ss.SSS'`。禁止转为 ISO UTC 字符串（如带 `Z`），防止因客户端时区转换导致日期偏移一天。
4. **防重机制（Idempotency-Key）**：
   - 所有单据创建、保存、批量操作等写接口，请求头必须支持携带 `Idempotency-Key`。
   - 表 `sys_idempotent_key` 已建（唯一键 idem_key+user_id，status PENDING/DONE，存 http_status 和 response_json）；拦截器待 WP01 实现。约定：首次接收置 `PENDING`，完成后存响应并置 `DONE`；重复请求回放原 HTTP 状态和原返回体；同键请求仍在处理时返回 `SYS_IDEMPOTENT_IN_PROGRESS`（409）。`SYS_IDEMPOTENT_REPLAY` 暂保留不用。
5. **并发更新乐观锁（version）**：
   - 单据头表自带 `version INT NOT NULL DEFAULT 0`。
   - 执行 `PUT` 或修改保存时，SQL 必须带 `WHERE version = ?` 并令 `version = version + 1`。若影响行数为 0，立即抛出 `BIZ_VERSION_CONFLICT`（映射 HTTP 409），前端提示“数据已被他人修改，请刷新”。

## 5. 单据状态机

> **状态**：常量与类型已实现（[packages/shared/src/status.ts](packages/shared/src/status.ts)、[state-machine.ts](packages/shared/src/state-machine.ts)）；状态机驱动引擎约定待 WP02 实现。

### 5.1 SM-01 通用状态模型
单据头状态由一个核心主状态（`status`）与三个独立维度共同决定：
- **主状态（`status`）**：`DRAFT`（暂存）、`CREATED`（创建）、`AUDITING`（审核中）、`AUDITED`（已审核）、`REAUDIT`（重新审核）。
- **关闭维度（`close_status`）**：`A`（正常）、`B`（已关闭）。
- **作废维度（`cancel_status`）**：`A`（正常）、`B`（已作废）。
- **禁用维度（`forbid_status`）**：`A`（启用）、`B`（禁用，主要用于基础资料）。

### 5.2 操作流转前置条件与结果矩阵表
下表是状态机执行操作的唯一裁决准则：

| 操作代码（`op`） | 操作名称 | 允许前置状态（`from`） | 目标状态（`to`） | 前置维度要求 | 维度变更 | 权限项（`perm`） | 业务说明与约束 |
|---|---|---|---|---|---|---|---|
| `save`（draft） | 暂存 | 新建 / `DRAFT` | `DRAFT` | 正常（非作废、非关闭） | — | `new`/`edit` | 跳过必录与唯一性校验 |
| `save`（save） | 保存 | 新建 / `DRAFT` / `CREATED` / `REAUDIT` | `CREATED` | 正常（未作废、未关闭） | — | `new`/`edit` | 强校验必录、唯一；初次生成编号 |
| `submit` | 提交 | `DRAFT` / `CREATED` / `REAUDIT` | `AUDITING` | 正常（未作废、未关闭） | — | `submit` | 先自动保存校验；挂流程则启动流程实例 |
| `unsubmit` | 撤销 | `AUDITING` | `REAUDIT` | 正常（未作废、未关闭） | — | `submit` | 挂审批流时按第 8 节撤回规则（`allowWithdraw`） |
| `audit` | 审核 | `AUDITING` | `AUDITED` | 正常（未作废、未关闭） | — | `audit` | 流程终审同意时由系统调用；扣减库存与反写 |
| `unaudit` | 反审核 | `AUDITED` | `REAUDIT` | 正常（未作废、未关闭） | — | `unaudit` | **下游有有效单据时禁止反审核**；回滚反写 |
| `close` | 关闭 | `AUDITED` | 保持不变 | `close_status='A'` | `close_status='B'` | `close` | 业务中止，禁止后续下推流转 |
| `unclose` | 反关闭 | `AUDITED` | 保持不变 | `close_status='B'` | `close_status='A'` | `close` | 恢复正常状态 |
| `cancel` | 作废 | `CREATED` / `REAUDIT` | 保持不变 | `cancel_status='A'` | `cancel_status='B'` | `cancel` | **已审核必须先反审核才能作废**；释放占用 |
| `uncancel` | 反作废 | 任意 | 保持不变 | `cancel_status='B'` | `cancel_status='A'` | `cancel` | 回复到 `cancel_prev_status` |
| `delete` | 删除 | `DRAFT` / `CREATED` | 删除（物理删除还是标记删除由 WP02 定） | 正常（未作废、未关闭） | — | `delete` | 仅允许删除暂存或未审核草稿 |
| `forbid` | 禁用 | 任意（基础资料） | 保持不变 | `forbid_status='A'` | `forbid_status='B'` | `forbid` | 基础资料停用，禁止新单据引用 |
| `unforbid` | 反禁用 | 任意（基础资料） | 保持不变 | `forbid_status='B'` | `forbid_status='A'` | `forbid` | 恢复基础资料启用 |
| `reject` | 审批驳回 | `AUDITING` | `REAUDIT` | 正常（未作废、未关闭） | — | 系统内部 | 流程节点驳回时内部调用，不对外开放 |

> **核心红线**：
> 1. **作废红线**：禁止对处于 `AUDITED`（已审核）状态的单据直接执行 `cancel`！必须先执行 `unaudit`（反审核）使其回到 `REAUDIT`，方可执行作废。
> 2. **反审核红线**：单据若存在下游有效单据（`sys_bill_link` 中存在关联且下游未作废、未删除），状态机必须直接拦截并抛出 `BIZ_HAS_DOWNSTREAM`，严禁强制反审核。

### 5.3 职责分离（SOD）规则
单据元数据中配置的 `options.sod` 在执行操作时由引擎强制校验：
- `auditorNotCreator`：审核人（`auditor_id`）不得等于单据创建人（`creator_id`）。违规报 `BIZ_SOD_VIOLATION`。
- `unauditBySameAuditor`：反审核执行人必须与原审核人相同。
- `editByCreatorOnly`：仅允许单据创建人修改单据。
- `deleteByCreatorOnly`：仅允许单据创建人删除单据。

### 5.4 字段锁定（FieldLockRule）与运行时视图取舍

> 取舍：在 `packages/shared/src/state-machine.ts` 中，`FieldLockRule` 的注释为“该状态下可编辑的头字段（白名单）”；而在 `bill-meta.ts` 中，`BillView.lockedFields` 为返回给前端的结构。两者的语义转换约定如下：
> - **配置态（`FieldLockRule`）**：开发者在配置状态机字段锁定时，配置的是**允许编辑的白名单**（`'*'` 表示全部可编辑，`[]` 表示全部锁定，`['remark']` 表示仅 remark 允许编辑）。
> - **运行时（`BillView.lockedFields`）**：单据引擎向前端输出详情时，将配置白名单与用户的字段权限计算差集，转换为**前端需禁用的黑名单**（`lockedFields: { header: string[] | '*', entry: string[] | '*' }`）。
> - 当且仅当状态机配置为 `[]` 时，输出 `lockedFields.header = '*'`（整单禁用）；当配置为 `['remark']` 时，引擎将除 `remark` 以外的所有元数据字段 key 填充进 `lockedFields.header` 数组。前端只需判断：`const isLocked = view.lockedFields.header === '*' || view.lockedFields.header.includes(fieldKey);`。

### 5.5 行级状态机（`RowStatusConfig`）与执行至
在生产订单（`pp_mo_entry`）等单据中，分录存在独立的生命周期流转：
```typescript
// packages/shared/src/state-machine.ts
export interface RowStatusConfig {
  entity: 'entry';
  field: string;          // 物理列名，如 'biz_status'
  initial: string;        // 初始状态，如 'PLANNED'
  states: { code: string; name: string }[];
  transitions: RowTransition[];
}
```
生产订单行业务状态链（状态代码为示例，以 WP06 定稿为准；需求说明书 SM-04 的中文名为 计划/计划确认/下达/开工/完工/结案）：`PLANNED`（计划） $\rightarrow$ `CONFIRMED`（确认） $\rightarrow$ `RELEASED`（下达） $\rightarrow$ `STARTED`（开工） $\rightarrow$ `FINISHED`（完工） $\rightarrow$ `CLOSED`（结案）。
- **执行至（`exec_to?target=RELEASED`）**：引擎按 `direction: 'forward'` 寻找路径，自动经过 `jumpable: true` 的中间节点，并按序触发绑定的 `hook` 守卫检查。
- **反执行至（`exec_to?target=PLANNED`）**：按 `backward` 寻找逆向路径，检查下游领料、报工等业务关联，安全回退。

反写校验与关闭判定完全由安全表达式引擎 [packages/shared/src/expr.ts](packages/shared/src/expr.ts) 解析执行，绝不使用 `eval`。

#### 内置函数列表
表达式引擎支持四则运算、三元判断（`a ? b : c`）、属性访问（`head.org_id`、`entry.qty`）及以下内置安全函数：
`ceil`、`floor`、`round(x, n)`、`abs`、`min(...args)`、`max(...args)`、`if(c, a, b)`、`isnull(x, default)`、`len(s)`、`contains(s, sub)`、`in(x, ...rest)`、`issueLimit(...)`。

#### 领料超发控制上限函数（`issueLimit`）
在生产用料清单领料控制中，超发上限由 `expr.ts` 原生导出的 [issueLimit](packages/shared/src/expr.ts) 函数裁决：
$$\text{issueLimit}(mode, mustQty, stdQty, scrapRate, minIssueQty)$$
计算逻辑：
1. `mode = 'ALLOW'`（或 `'1'`）：允许无限制超发，返回 $\infty$（`1e30`）。
2. `mode = 'MIN_BATCH'`（或 `'2'`）：按最小发料批量超发。若 $minIssueQty \le 0$ 返回 $mustQty$；否则返回：
   $$\lceil mustQty / minIssueQty \rceil \times minIssueQty$$
3. `mode = 'SCRAP'`（或 `'4'`）：按物料标准损耗率超发，计算公式为：
   $$stdQty \times (1 + scrapRate / 100)$$
4. 其余模式（`'FORBID'`、`'3'`）：严格不允许超发，返回 $mustQty$。

### 6.5 并发控制与事务边界规范
为保证在多用户、高频报工及并发审核下数据的一致性，下推与反写必须遵循以下执行律：
1. **行锁加锁顺序（防死锁）**：
   在单据审核、保存反写上游时，若需要锁定多条上游单据行，**必须按上游行主键升序（`ORDER BY id ASC`）依次执行 `SELECT ... FOR UPDATE`**，严禁乱序加锁导致 MySQL 死锁。
2. **增量 UPDATE**：
   累加数量必须使用原子增量 SQL，严禁“查出原值 $\rightarrow$ 内存相加 $\rightarrow$ UPDATE 回写”：
   ```sql
   UPDATE scm_pur_req_entry 
   SET link_qty = link_qty + ? 
   WHERE id = ?;
   ```
3. **两段反写生命周期**：
   - 下游单据**保存**：增加上游 `link_qty`（选单占用）；下游**删除**或**作废**：扣减上游 `link_qty`（释放占用）。
   - 下游单据**审核**：增加上游 `order_qty`（累计执行数）；下游**反审核**：冲减上游 `order_qty`。（需求说明书 5.1 第 1 条、R26）
4. **同一事务边界**：
   下游单据自身状态变更、上游行锁与反写、库存更新（`scm_inventory` 与 `scm_inv_txn`）、链路登记（`sys_bill_link`）必须包裹在同一个 [DbService.tx](apps/api/src/db/db.service.ts) 事务内。
5. **提交后回调（`afterCommit`）**：
   WebSocket 推送、异步通知、`sys_event_outbox` 触发事件必须通过 `DbService.afterCommit(() => { ... })` 调度，确保事务提交后再对外发射，避免读到未提交脏数据。

### 7.1 功能权限模型
- **模型**：业务对象代码（`objectCode`，如 `'scm_pur_req'`） $\times$ 权限项代码（`permCode`，见 `PermItems`）。

## 8. 审批流接入

> **状态**：模型契约已实现（[packages/shared/src/workflow.ts](packages/shared/src/workflow.ts)）；BPMN 引擎、任务调度与设计器服务端约定待 WP03 实现。

### 8.1 四层流程架构定位
根据技术方案 5.1 与需求说明书 6.1，系统严格划分四层流转机制：
- **L1 单据状态机**（`bill-engine/state`）：单据本体状态、操作前置条件、字段锁。
- **L2 审批流引擎**（`workflow`）：单据提交后进入多级审批，负责任务生成、会签裁决、委托。
- **L3 业务流程**（`bill-engine/flow`）：一期支持“单据审核通过后自动下推”。
- **L4 转换与反写**（`bill-engine/convert|writeback`）：跨单据字段带值与累计数量更新。

### 8.2 单据与审批流引擎交互契约
1. **提交（`submit`）**：
   L1 校验单据处于 `DRAFT` / `CREATED` / `REAUDIT`，若该单据类型挂了启用的流程模板（`sys_bill_type.wf_template_id`），单据状态变更为 `AUDITING`，并在**同一事务**内由 L2 创建流程实例、派发待办（wf_ 表待 WP03 新增）。未挂流程时变更为 `AUDITING`，由有审核权的人审核；`options.autoAuditAfterSubmit=true` 时提交后自动审核；`BIZ_WF_REQUIRED` 用于必须挂流程的单据。
2. **终审通过回调**：
   当流程实例流转至结束事件（`endEvent`）时，L2 引擎必须在同一数据库事务中回调 L1 的 `audit` 接口。若审核发生业务异常（如库存不足、反写超额），整个事务回滚，流程任务保留在终审节点并向审批人提示错误信息。
3. **驳回（`reject`）**：
   驳回到发起人：流程实例置 `REJECTED`，单据经内部操作 `reject` 变为 `REAUDIT`；驳回到中间节点：单据保持 `AUDITING`，从该节点重新生成待办（技术方案 5.3 用例 6）。
4. **撤回（`withdraw`）**：
   当后续节点处理人尚未审批时，发起人可撤回申请。流程实例置 `WITHDRAWN`，单据变更为 `REAUDIT`。

### 9.3 `BizError` 抛出与逐行错误示例
```typescript
import { BizError } from '../common/biz-error';
import { ErrorCodes, RowError } from '@erp3d/shared';

// 单字段业务校验阻断
if (approveQty.lte(0)) {
  throw new BizError(ErrorCodes.BIZ_FIELD_INVALID, '批准数量必须大于 0', {
    errors: [{ entity: 'entry', row: 1, field: 'approve_qty', msg: '批准数量必须大于 0' }]
  });
}

// 批量分录多行校验阻断
const rowErrors: RowError[] = [];
entries.forEach((row, idx) => {
  if (!row.material_id) {
    rowErrors.push({ entity: 'entry', row: idx + 1, field: 'material_id', msg: '分录物料不能为空' });
  }
});
if (rowErrors.length > 0) {
  throw new BizError(ErrorCodes.BIZ_REQUIRED, '分录数据校验失败，请检查必填项', { errors: rowErrors });
}
```

### 10.2 `DbService` 数据库操作接口
业务代码禁止引入 TypeORM Repository 实体层，统一注入 `DbService` 执行原生 SQL 与事务管理：
- `q<T>(sql, params)`：执行查询。若当前在事务中则自动走事务连接，否则从池中借出连接。
- `one<T>(sql, params)`：查询单条记录，不存在返回 `undefined`。
- `exec(sql, params)`：执行 DML，返回 `{ affectedRows, insertId }`。
- `tx<T>(fn, opts)`：开启事务（隔离级别严格为 `READ COMMITTED`，彻底规避间隙锁 Gap Lock 导致的死锁）。支持事务嵌套；遇到 `ER_LOCK_DEADLOCK` 或 `ER_LOCK_WAIT_TIMEOUT` 自动按退避算法重试 3 次。
- `afterCommit(fn)`：注册事务提交后回调。
- `independent<T>(fn)`：开启与外层解耦的独立事务，专用于流水号生成。
- **标识符防注入**：拼接表名、列名必须强制经过 [ident(name)](apps/api/src/db/db.service.ts) 校验转义，仅允许字母、数字与下划线。

### 10.3 迁移脚本命名与显式登记规范
由于生产镜像打包排除了动态 Glob 扫描，所有迁移必须遵循严格的显式登记机制：
1. **命名规范**：`apps/api/src/db/migrations/<timestamp>-<ModName>.ts`。时间戳为毫秒（如 `1794500000001`）。
2. **显式登记**：新建迁移后，必须立即将其导入并追加至 [apps/api/src/db/migrations/index.ts](apps/api/src/db/migrations/index.ts) 的 `ALL_MIGRATIONS` 数组中。
3. **幂等编写三原则**：
   - 只能使用 `ensureTable`、`addColumnIfMissing`、`addIndexIfMissing`、`upsert` 工具函数。
   - **严禁编写 `DROP TABLE`、`DROP COLUMN` 或改写现有列数据类型**。
   - 保证迁移脚本可反复执行多次，且每次执行产生相同的数据库状态（Idempotent）。

### 10.4 共享数据库红线守则
根据技术方案第 7 章（数据库与金融平台共用 lustone 的 MySQL 容器），全栈开发必须恪守以下四条铁律：
1. **连接池硬上限**：ERP 应用总连接数在生产环境不得超过 30。`apps/api/src/config/config.ts` 已内置限制：`poolMax = Math.max(1, Math.min(poolMax, 30))`，默认配置 20。
2. **严禁修改全局参数**：严禁执行 `SET GLOBAL ...`，严禁修改全局 SQL 模式或服务器时区，所有个性化配置必须限定在会话（Session）级别。
3. **严禁重度大表全表扫描**：复杂跨域报表必须使用汇总表或加锁前的索引过滤，禁止在业务主库执行无索引关联的笛卡尔积分析。
4. **统一专用库与账号**：应用层仅对 `erp3d` 库拥有完整权限，严禁探测或跨库访问金融平台同实例下的其他 Schema。

   - 生产补料单（R08）：混杂不同发料组织、生产组织、货主的分录，触发自动下推，验证严格按“发料组织 + 生产组织 + 货主 + 货主类型”聚合生成对应张数的单据头。

### 13.2 元数据驱动渲染协议（Metadata-Driven UI）
前端单据页面不得硬编码表单项，统一基于后端元数据动态生成：
1. **元数据装载**：页面加载时请求 `GET /api/v1/meta/bills/{form}`，获取 `BillMeta`。
2. **表单自动构建**：
   - 表头按 `meta.header` 中的字段类型映射 Element Plus 组件：`string` $\rightarrow$ `el-input`；`qty`/`amount` $\rightarrow$ `el-input-number`（禁用步进器，靠右对齐）；`date` $\rightarrow$ `el-date-picker`；`ref` $\rightarrow$ 弹窗选择器。
   - 分录表格按 `meta.entry.fields` 生成表格列。
3. **单据详情接口（`BillView`）消费**：
   详情接口 `GET /api/v1/bills/{form}/{id}` 返回以下标准结构：
   ```typescript
   // packages/shared/src/bill-meta.ts
   export interface BillView {
     form: string;
     header: Record<string, unknown>;
     entries: Record<string, unknown>[];
     allowedOps: string[]; // 当前单据状态下允许操作的操作按钮列表
     lockedFields: { header: string[] | '*'; entry: string[] | '*' }; // 需锁定的字段
     lock?: { userId: number; userName?: string; lockedAt: string } | null;
     wf?: { instanceId: number; status: string; currentNodes: string[] } | null;
   }
   ```
4. **前端状态绝对依从原则**：
   **单据页面顶部操作按钮的高亮/禁用、表单各字段的可编辑性，必须 100% 依从后端返回的 `allowedOps` 与 `lockedFields`**！前端禁止在本地自行根据 `status === 'CREATED'` 编写硬编码判断逻辑。

### 13.3 接口调用、拦截与错误反馈
- 鉴权请求头：除登录、公开接口外，所有请求头必须自动附带 `Authorization: Bearer <accessToken>`。
- 401 自动无感刷新：当响应码为 401 时，Axios 拦截器自动拦截并暂存请求队列，使用 `refreshToken` 调用 `POST /api/v1/auth/refresh`。刷新成功后重放队列；刷新失败立即清空登录态并跳至登录页。
- 业务错误提示：拦截器统一判断 `code !== 'OK'`，使用 `ElMessage.error(msg)` 全局告警；若返回包含 `errors` 数组，表单定位至对应行与控件红框高亮。
- 幂等请求头：所有保存、提交、批量操作，Axios 拦截器自动在 Header 附加 `Idempotency-Key: <UUID>`。
- Mock 开关（wp16 分支 WIP 现状）：`.env.development`/`.env.production` 里 `VITE_USE_MOCK=true`（后端未就绪），URL `?mock=0|1` 或 localStorage `erp.mock` 可临时覆盖；后端联调时改为 false，Vite 把 `/api` 代理到 `http://localhost:3000`。
- 字段名：接口一律 snake_case（与元数据 key 一致）。wp16 WIP 的前端类型是 camelCase 视图模型，接后端时需加一层适配（待 WP16 恢复后做）。
- WebSocket 连接：使用 `socket.io-client` 连接 `/ws`，握手携带 `{ auth: { token } }`，统一监听 `msg.new`、`todo.changed`、`bill.changed` 并触发 Pinia Store 状态响应。

### 14.1 架构取舍与差异汇总表
