# WP02/WP03 独立复核

复核基线：`2b0fdff..HEAD`，分支 `wp03-workflow`。对照 `docs/平台开发约定.md` 与 `/workspace/erp-3d/fullsys/交接-临时GPT.md`。审查发现 5 项真实问题，均已修复；没有提交或访问服务器。

## 问题与处理

1. **P1：流程历史绕过单据查看权限和数据范围。** 原 `WfBillController` 直接将请求交给 `WfQueryService.flow`：

   ```ts
   @Get(':form/:id/flow')
   flow(@Param('form') form: string, @Param('id', ParseIntPipe) id: number) {
     return this.query.flow(form, id);
   }
   ```

   `WfQueryService.flow` 按 `form`、`bill_id` 直接读取实例、待办和意见，没有权限或组织范围过滤，能暴露审批人、处理意见及审批记录。现由 [wf.controller.ts](../apps/api/src/workflow/wf.controller.ts:144) 先调用 `BillQueryService.view`，继承单据查看权限和数据范围检查；[07-approval.e2e-spec.ts](../apps/api/test/engine/07-approval.e2e-spec.ts:327) 验证无查看权限的用户收到 `PERM_DENIED`。

2. **P1：工作流终审绕过 SOD。** 原审核判断包含内部操作豁免：

   ```ts
   if (meta.options?.sod?.auditorNotCreator && Number(h.creator_id) === user.id && !opts.internal) {
   ```

   工作流回调以 `{ internal: true, user }` 调用标准审核，故制单人可作为最后审批人完成审核，违反约定 5.3。已去掉对 `internal` 的豁免，仍由最终审批人身份检查；[bill-op.service.ts](../apps/api/src/bill-engine/service/bill-op.service.ts:278) 和 [07-approval.e2e-spec.ts](../apps/api/test/engine/07-approval.e2e-spec.ts:338) 可核对修复及回滚断言。

3. **P2：工作流撤回与终审存在锁顺序反转。** 原 L1 顺序为先锁单据头再调用 workflow bridge：

   ```ts
   const h = await this.store.mustHeader(form, id, { forUpdate: true });
   // ...
   await bridge?.onUnsubmit?.(ctx);
   ```

   原 `lockInstance` 直接锁实例，终审/流程撤回随后回调 L1 锁单据头：

   ```ts
   'SELECT * FROM wf_instance WHERE id = ? FOR UPDATE'
   // ...
   if (updateBill) await this.bills.rejectByWorkflow(inst.form, inst.bill_id, user);
   ```

   两条路径可能形成 bill → instance 与 instance → bill 的死锁环。`WfEngine.lockInstance` 现在先读实例标识，再按统一顺序锁单据头、实例，仍在其后锁任务；设计说明已同步。回归用例并发触发终审和撤回，验证只出现一致的两种终态之一（`COMPLETED/AUDITED` 或 `WITHDRAWN/REAUDIT`）：[wf-engine.service.ts](../apps/api/src/workflow/wf-engine.service.ts:224)、[WP03 设计](WP03-审批流设计.md:11)、[审批 E2E](../apps/api/test/engine/07-approval.e2e-spec.ts:367)。

4. **P2：连接池可配置到 10，超过本次每台 ≤9 的硬约束。** 原配置：

   ```ts
   poolMax: Math.max(1, Math.min(poolMax, 10)),
   ```

   与本次交接的上限不符。已钳制为 9，并同步 `.env.example`、平台约定 15.1 和部署测试：[config.ts](../apps/api/src/config/config.ts:52)、[03-deploy.e2e-spec.ts](../apps/api/test/03-deploy.e2e-spec.ts:44)、[平台开发约定](平台开发约定.md:1101)。端口默认仍为 8080。

5. **P1：源码和环境示例含固定凭据回退值。** 原配置与示例分别包含：

   ```ts
   password: process.env.DB_PASSWORD || '***',
   secret: process.env.JWT_SECRET || '***',
   refreshSecret: process.env.JWT_REFRESH_SECRET || '***',
   ```

   ```dotenv
   DB_PASSWORD=***
   JWT_SECRET=***
   JWT_REFRESH_SECRET=***
   ```

   （上传仓库时已将上文示例中的具体回退值替换为 `***`，以免把旧密钥再次写入新提交；完整 git 历史中仍可能出现原文。）生产漏配时会使用已知凭据。已移除固定回退值，生产配置缺少任一变量时启动即报错，`.env.example` 对应项改为空：[config.ts](../apps/api/src/config/config.ts:43)、[.env.example](../apps/api/.env.example:7)、[部署 E2E](../apps/api/test/03-deploy.e2e-spec.ts:63)。MinIO 凭据仍只从 `S3_*` 环境变量读取。

## 其他约定核查

- 作废在审核状态下明确拒绝；反审核查询有效下游并报 `BIZ_HAS_DOWNSTREAM`。两段反写分别在保存和审核触发，反写及冲回均按表名、分录主键升序锁行：见 [bill-op.service.ts](../apps/api/src/bill-engine/service/bill-op.service.ts:192)、[writeback.service.ts](../apps/api/src/bill-engine/service/writeback.service.ts:92)。
- 最后审批人通过时，L2 在结束实例的事务内调用 L1 `auditByWorkflow`；回调要求 `DbService.inTx`，审核失败会回滚审批结果和单据审核，见 [wf-engine.service.ts](../apps/api/src/workflow/wf-engine.service.ts:171) 与 [bill-op.service.ts](../apps/api/src/bill-engine/service/bill-op.service.ts:139)。
- 整单驳回、流程撤回、退回已走节点分别更新单据和流程状态；会签、代理、转交及加签都有行为测试。自定义业务事件通过 `BillEventDef.handler/undoHandler` 扩展，且已有事务回滚和 outbox E2E（`06-custom-event.e2e-spec.ts`）。
- 审批实例、任务、变量与动作历史持久化在 `wf_*` 表；进程内定时器只保存任务定义，防重复执行使用 MySQL `GET_LOCK`，无跨请求审批状态。迁移显式登记且使用 `ensureTable`；新增部署用例在测试库连续运行工作流迁移两次。
- 未发现新增 SQL 注入路径：用户值均用参数绑定，动态表列名经过 `ident` 白名单校验；BPMN 解析器拒绝 DTD/实体声明。写回行锁和工作流终审/撤回锁顺序已覆盖上述并发检查。
