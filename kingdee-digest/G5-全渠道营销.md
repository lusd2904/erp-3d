## 1. 功能点

### 1.1 促销管理（`全渠道营销_促销管理.md`）

- 全程：促销申请 → 促销政策 → 订单匹配执行 → 促销结案。路径在【分销与流通】－【促销管理】。概述写明覆盖分销渠道常用的折扣、赠品、整单、特价。
- 使用前在销售组织启用【促销管理系统参数】。两项：启用促销管理（未启用则销售订单不能匹配）；是否叠加执行多个促销政策（不启用则只执行一个）。
- 基础资料链：促销类型 → 促销方式 → 促销模式 → 促销政策上的属性列随模式变化。费用项目与【基础管理】－【基础资料】－【公共资料】－【费用项目】同一实体。
- 预置促销类型两种：即时奖励促销、售后返利促销。本版促销管理只展开即时奖励，即销售订单下单时匹配执行。售后返利的计算与结算在返利管理。
- 预置 8 种促销方式，均为即时奖励，系统预置不允许修改和删除：单品买赠、组合买赠、组合买赠并折扣、单品折扣、组合折扣、整单折扣、组合价格、换赠促销。
- 促销政策：创建组织、币别（默认本位币）、参与销售组织及起止时间、参与客户或客户类别。可从已有效的促销申请带出。规则包括：赠品种类限制（全赠，或指定赠送品种数量后从多种赠品中选）；多组号执行策略为并行或串行（默认串行）；促销折扣是否支持折上折；组号表示一种促销实例，组合方式为任意组合或固定组合，物料分组与物料编码互斥；条件为购买数量或购买金额；赠品分「赠品」与「换赠」（换赠要填促销价格）；赠品赠送基数不填则满足条件只赠一次，填写则按数量或金额对基数取整循环赠送（原文例：买 10 赠 2、基数 10，买 135 赠 26）；折扣方式为折扣率或折扣额，另有整单折扣率、整单折扣额；促销例外按物料分组或物料排除；可失效 / 取消失效。
- 促销执行：按销售组织、客户、业务日期匹配，按购买数量或购买金额校验。销售订单保存或提交后可手工匹配，确定后把折扣、赠品、促销价格回写订单。B2B 电商门户下单自动匹配并记到分录。可取消匹配。差异数量 = 实际数量 − 购买数量，小于 0 表示数量条件不满足；差异金额同理。
- 促销申请单：单据类型默认「商品促销类型」。表头有主题、申请组织/部门/人、开始结束日期、促销目标、品种范围、客户范围、预计促销总费用、预计销售总收入、预计促销利润增长%。预计费用金额 = 数量 × 单价。费用项目不含存货成本类型。
- 促销结案报告：前提是促销申请已审核。实际促销总费用、实际销售总收入由系统汇总表体；实际促销利润增长%手工填。总体目标达成率% = 实际销售总收入 / 预计销售总收入 × 100%。总体促销效果手工四档：效果很好、较好、一般、不好待改进。行目标达成率按实际销售收入 / 预计销售收入 × 100%（公式句用词是「实际收入」，字段名是「实际销售收入」）。行促销效果：达成率 ≥100% 成功，≥80% 合格，低于 80% 失败。结案后申请为已结案，可取消结案再结。
- 应用流程第三步两个入口：【供应链】－【销售管理】－【订单处理】－【销售订单】；【客户订货平台】－【在线订货】－【购物车】－【下单】。流程页写「在网上订单中执行促销政策」。网上订单与销售订单的字段差异未写。

### 1.2 返利管理（`全渠道营销_返利管理.md`）

- 激励经销商/大客户。支持年度、月度、季度及自定义周期。按政策和销售数据计算，结算支持冲账、返现、返物。原文写：使企业通过对销售返利降低销售收入、从而降低销售利润。该句没有科目与时点。
- 流程：基础资料 → 返利政策 → 返利数据准备 → 返利计算平台（符合条件自动生成返利结算单）→ 返利结算。使用流程里写了两个「第四步」。
- 预置返利类型一种：直接售后返利，可自定义。预置 4 种返利方式：年度返利-按购买金额返点、年度返利-按购买数量返点、月度返利-按购买金额返点、月度返利-按购买数量返点。返还形式原文列举：冲减应收款、其它应付款、赠品出库、返利、返还到账户余额，并写「等四种」。
- 周期类型：年度、半年度、季度、月度及自定义。系统预置一年的月度周期。
- 返利模式 = 类型 + 方式。返利对象类型：客户、客户分类。返利依据单据：销售出库单、应收单。折扣方式三种：返利率、单位返利额、固定返利额。另有赠品、赠送数量、赠送基数。
- 返利政策：返利组织为有结算属性的业务组织。累进方式：全额累进、超额累进（原文只点名，没有分段算法）。表体含返利周期、组号、物料分组或物料编码（互斥）、购买数量、购买金额、指标数量、指标金额、指标完成率、赠品及赠送数量/基数、返利率%、单位返利额。须审核后才有效。政策表体字段列表未出现固定返利额。
- 组织参数「返利管理系统参数」只有一项：叠加执行返利政策。同一周期同时满足多个政策时，启用则叠加，否则只允许一个政策。
- 销售数据准备：按返利组织、政策、周期起止，从销售出库单或应收单统计购买数量、购买金额。按指标数量时完成率 =（实际数量/指标数量）×100%，取两位小数；按指标金额同理。该页后半又有一段写销售订单保存或提交后做返利匹配并把折扣、赠品、返利价格返回订单，与同页统计口径以及模块的售后计算定位冲突，见第 5 节。
- 返利计算四步：选政策 → 自动调取准备数据 → 计算 → 确定后生成返利结算单，销售准备数据打上已完成标记，不允许重复计算。公式：返利率时，应返利金额＝实际销售金额×返利率；单位返利额时，应返利金额＝实际销售数量×单位返利额；赠品时，赠品数量＝（实际销售数量/赠送基数）×赠送数量。
- 返利结算单返还方式：冲减应收款、其他应付款、赠品出库返还、返还到账户余额。下游：冲减应收 → 红字其他应收单；其他应付 → 其他应付单（原文称为返现）；赠品出库 → 其它出库单；返还到账户余额 → 累加该客户该账户余额。结算页功能概述写成「对返利进行结案分析」，使用前提写成「返利申请已经审核」。本模块没有名为返利申请的单据页。以字段和操作说明为准：它是结算单。
- 返利账户：账号、户名、数据状态，是否默认账户只允许一个默认。返利余额流水：增加为正、扣减为负。币别说明原文「当前置为人民币」。
- 返利余额使用规则：按账户、按客户。是否指定商品范围（否=订单全部商品）。是否支持促销活动（是=促销执行后仍可用本规则；否=订单执行促销后不允许使用本返利规则）。表体：客户类别或客户、订单金额>=、订单金额使用比例、开始/结束日期。原文示例：订货金额必须大于 1000，订单金额 20% 可用账户余额；使用额度作为分录商品折扣扣减应付货款。网上订单下单时可使用返利账户支付货款。
- 数据准备页写「本版暂只支持返利对象为客户」；结算单写「目前为客户类型」。模式上仍可勾选客户分类。分类返利是能力声明与「本版只支持客户」并存。
- `全渠道营销_BBC分销商门户.md`「返利余额」页路径是【电商与分销】→【返利管理】→【返利余额】。字段含核算组织、返利账户、客户（一个客户可多个返利账户）、币别、返利余额、是否初始化。新增只用于录入初始余额，提交审核后结束初始化。余额调整：正数增加、负数减少。无初始化余额时，第一笔结算金额会自动结束初始化。返还方式写在「更新日期」行的说明里。

### 1.4 营销费用管理（`全渠道营销_营销费用管理.md`）

- 概述：营销费用常达营业额的 15%–40%（原文行业泛述）。按经销商每月或每年销售业绩做费用预算，确定可用额度；然后每月申请、执行、报销、分析、调整。
- 特性：模板配置化（举例费用场景：堆头费、进场费）；预算、申请、执行、核销、报表分析一体化；没有预算不能申请，申请必须执行，没有执行不能报销。
- 营销费用申请、营销费用执行、营销费用报销都在【BBC移动端】－【营销费用】。申请在费用发生前，可上传附件。执行由稽查人员对活动现场效果、商品摆放、活动规范性拍照取证，记到费用执行单。报销在费用发生后，可上传附件。
- 系统参数在【业务中心】－【系统】－【系统参数】－【营销费用管理】：选择申请单员工后，移动端申请时 Cloud 默认申请人为该员工，且每个客户有且只有一个默认申请人。
- 预算编制指向【金蝶AI星空】－【管理会计】－【预算管理】。说明只有两句：编写预算控制规则与控制范围；编写预算值，支持多维度。无维度清单。「分析」「调整」在概述出现，操作手册没有对应页。申请、执行、报销、预算都没有字段表。

### 1.5 要补货管理（`全渠道营销_要补货管理.md`）

- 定位：以渠道为销售模式的制造企业，做渠道协同和产销协同。特性：层级渠道、配送网络、智能要货、要货集中处理、智能补货。概述写「K3Could 要补货管理」。四种模式并可扩展，概述用词为采购直送、统购通配、直接配送、购销配送。补货模式页的四个正式名称是：直接配送、购销配送、采购直送、统购统配。直接配送与购销配送属于通过库存补货模式；采购直送与统购统配属于通过采购补货模式。原文写目前版本支持用户自定义。
- 五条业务流程均只有图，文字摘要：渠道补货-供货组织铺货；智能要货-直接配送；智能要货-购销配送；智能要货-统购统配；智能要货-采购直送。流程步骤只在图里。
- 实施顺序：公共基础资料 → 分销管理系统参数 → 渠道、配送网络、物料分销特性。多组织下新建渠道前，必须先有对应组织及内部客户、内部供应商。日常：要货管理、补货管理、配货管理、要货处理中心。
- 渠道网络（路径在【营销网络】－【分销渠道】）：本版本渠道归属锁定为内部渠道。对应组织必填。编码前缀「QDDA」。原文写默认新增仓库均参与 DRP。共享型基础资料。
- 配送网络：要货渠道、供货库存组织、供货仓库、组织间结算价目表。字段表有列错位，见第 5 节。
- 物料分销特性：功能说明写最大/最小库存、要补货方案、补货模式、日平均销量等。字段表却只重复了四种补货模式。
- 要补货业务元素 YS001–YS018，本版不支持自定义。需求侧：销售订单未出库数量（订单数量−出库数量；不考虑按交货计划的明细交货信息；非暂存、未作废、未关闭、未取消）、要货申请单、配送单、补货单的未执行量。在途侧：要货申请单、采购申请单、配送单、补货单的未执行量。主数据含安全库存、现有库存（参与 DRP 的供货仓库即时库存且状态可用）、要补货批量、最小要补货批量、最大库存、最小库存、再订货点、送货周期(天数)、运输提前期(天数)、平均日销量。按物料+辅助属性汇总，数量转为销售计量单位。YS014 说明原文是「最大库存.最小库存」。
- 要补货业务要素 12 个，不支持自定义。YWYS001 需求来源 = YS001+YS002+YS003+YS004；YWYS002 在途 = YS005+YS006+YS007+YS008。YWYS010 要素名是要补货周期(天数)，对应元素 YS016 的字段名是送货周期。
- 要补货方案支持自定义公式。预置 6 个，公式照录：
  - YBHGS001 按需要货(默认)：净需求 = YWYS001 + YWYS003 − YWYS002 − YWYS004。无触发条件。
  - YBHGS002 按需要货：净需求同上。触发：(现有库存−安全库存) < (运输提前期天数 × 平均日销量)。
  - YBHGS003 按平均日销量补货：净需求 = 安全库存 + 平均日销量 × (送货周期天数 × 运输提前期天数) − (现有库存+在途)。触发与 YBHGS002 相同。原文把两个天数相乘。
  - YBHGS004 按再订货点补货：净需求 = 最大库存 − 现有库存。触发：现有库存 < 再订货点。
  - YBHGS005 按安全库存补货：净需求 = 现有库存 − 在途数量 + 安全库存。触发：现有库存 < 安全库存。公式按原文，结果方向原文未解释。
  - YBHGS006 按需补货（默认）：净需求同 YBHGS001。触发：(现有库存−安全库存) < 要货来源。公式里把 YWYS001 写成「要货来源」，要素名是「需求来源」。
- 建议量：先看最小订货量/最小补货量，净需求小于最小则取最小，否则取净需求；再按批量向上取整，最终 = 向上取整(a/b)×b。最小量或批量为空或 0 则不考虑该项。智能要货叫建议要货量，智能补货叫建议订货量，规则同文。
- 智能要货：渠道按方案算自己的需求并下达。供货类型默认要货申请，也可采购申请。智能补货：供货渠道算其配送网络中全部要货渠道，汇总成补货单；可立刻计算或按月/日/周调度（默认日）。
- 要货申请单：单据类型固定「标准要货申请单」，编号前缀 YHSQ。处理状态：待处理、已处理、打回。行关闭：关联数量 ≥ 批准数量则行关闭。作废后不能反作废。下游业务说明原文：直接配送 → 供货渠道配送单；购销配送 → 供货渠道销售订单；统购通配 → 供货渠道采购申请单或者配送单；采购只送 → 供货渠道采购申请单，直接配送要货渠道。正式模式名以补货模式页为准，见第 5 节。
- 补货单：类型「标准补货单」，前缀 BHD。可由智能补货生成。下游：下推供货渠道配送单；或下推要货渠道采购申请单并直接配送要货渠道。基本信息字段区混入智能要货结果字段；关闭规则文字仍写成「要货申请单的批准数量」。
- 配送单：类型「标准配送单」，前缀 PSD。下游：下推供货库存组织的分步式调出单。
- 要货处理平台：一次只处理同一供货渠道的多张要货申请单。直接配送、购销配送进「通过库存补货处理」；采购直送、统购统配送进「通过采购补货处理」。已处理的要货申请单不能再处理。业务说明的四种模式用词又是直接配送、购销配送、统购通配、采购直送。
- 分销配送平台：向导为订单选择 → 仓库选择 → 配货录入 → 配货清单，生成发货通知单。原文注：此为 3.0 版本的功能，不建议使用，高版本的要补货集中处理完全覆盖此项功能。
- 参数仅两项，字段名含「入库单单」：分销销售出库单审核时自动创建入库单，业务类型为分销购销；分销退料单审核时自动创建销售退货，业务类型为分销购销。操作手册另写参数路径名为「分销管理系统参数」。

## 2. 主要单据

### 2.1 促销与返利

- 促销申请单、促销政策、促销结案报告（`全渠道营销_促销管理.md`）。销售订单、网上订单、B2B 门户订单是匹配载体，促销文件不定义这些单据本身。基础资料：促销类型、促销方式、促销模式、费用项目、促销管理系统参数。

## 3. 可复用机制（面向电子元器件 ERP）

### 3.1 分销商门户（相关度 **高**）

来源：`全渠道营销_BBC业务中心.md`、`全渠道营销_BBC分销商门户.md`、`全渠道营销_BBC门店门户.md`。

- 按渠道性质分门户：直接渠道、中间渠道、终端门店看到的首页不同。B2C 与商家首页原文标明暂不支持。元器件可对应直营或分公司、代理商、方案商，菜单范围不同。登录取会员 ID 的原因原文没解释，经销商账号模型以渠道档案为准。相关度 **高**。
- 渠道档案把供货渠道、收货渠道、付款渠道拆开。仓储职能是收货资格，结算职能是付款资格。直接渠道向企业订货，中间渠道向指定上级订货。库存可自管进销存，或只上报库存；销量可自管开单，或只上报销量。允许负库存是开关。相关度 **高**。
- 可销范围三层：按渠道等级给标准价和折扣，按单个渠道追加，按例外剔除。发布组织可按销售组织隔离。相关度 **高**。渠道等级只有一个折扣率，没有阶梯、币别、有效期。相关度 **中**。
- 紧缺料用分货单：明细到末级渠道，或只卡中间节点总量；未订完可回收再分。可参考分货比例、渠道平均销量、分货等级。比例和平均销量没有计算公式。相关度 **高**。
- 常规料用建议订货量与最大可订货量卡住门户下单，并可与可用库存并行，再按商品或渠道豁免。机制相关度 **高**。自动计算公式写死 45 天周转、30 天日均、最大量=建议量×2.5，且声明不可自定义。这个常数相关度 **低**，元器件补货用要补货方案，不照抄该常数。分货结果按前一日 15:00 至当日 15:00 生效。时点相关度 **中**，原文没有解释为什么是 15:00。
- 门户下单：快速订货、列表订货、按主件查配件。向企业用 B2B企业订单 / B2B企业配件订单；向上级用 B2B渠道订单 / B2B渠道配件订单，且指定渠道订货固定先货后款、不显示在线支付。上级可改批准数量，并看到自己的即时库存和未发货数量。相关度 **高**。下游处理页把使用前提写成只有直接渠道，中间商能否处理下级订单，本页不能证明。
- 签收可部分收、可拒收，拒收可转补货数量，签收落成渠道入库。相关度 **高**。补货后续单据未写。物流公司与物流单号由销售出库单反写。相关度 **中**。没有配送路线、装车、运费计算。

- 渠道仓：入库、出库、盘盈盘亏、仓库级可销库存、0 库存不展示。初始化按法人及下属门店对账后结转期间库存。进销存可下查单据。企业可看下级经销商库存。相关度 **高**。入库单审核文字写成扣库存，不能当过账规则。我的商品串码只有标题，序列号不能据此立项。

- 营销关系树把行政组织与分货责任线拆开。相关度 **中**。业务目标体系、导购目标体系没有分解单据。
